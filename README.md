# KIMS SMART FACTORY

생산 제품의 수량과 상태를 관리하고, 디바이스 채널의 입력·출력 상태를 실시간으로 확인·제어하는 웹 애플리케이션입니다. 생산 입력, 제품·채널 관리, 디바이스 제어와 예약 기능은 회원 등급에 따라 제공됩니다.

## 주요 기능

- 생산 현황에서 제품별 누적 수량, 작업 수량, 목표 수량, 진행률, 상태와 변경 정보를 조회합니다. 달성률은 작업 수량 ÷ 목표 수량으로 계산합니다.
- 생산 현황과 생산 입력의 제품 선택은 사용자별로 `user_setting.product_view_selection`, `user_setting.product_control_selection`에 각각 저장합니다(`GET/PUT /api/me/product-selection/view`, `/api/me/product-selection/control`). 전체 선택은 `"*"`, 개별 선택은 제품 ID 문자열 배열, 모두 해제는 `[]`로 저장하며 재로그인이나 다른 브라우저에서도 복원됩니다. 기존 브라우저 선택은 DB에 저장된 설정이 없을 때 최초 조회 시 이전됩니다. 서버 재시작 시 기존 DB에 필요한 컬럼을 자동 추가합니다.
- 기본 12레벨 이상은 생산 입력과 생산 리포트를 이용합니다. 입력한 양수는 누적·작업 수량에 더하고 음수는 두 수량에서 뺍니다. 목표 수량은 생산 입력 화면에서 수정할 수 없습니다.
- 기본 14레벨 이상은 제품 등록·수정·삭제·정렬·사용 여부와 누적·작업·목표 수량을 관리합니다. 수량 수정에는 사유가 필요하며 이력이 저장됩니다.
- 기본 14레벨 이상은 채널 예약을 조회·등록·수정·중지·삭제하고 반복 예약과 실행 결과를 확인합니다.
- 기본 16레벨 이상은 회사 조직·회원·디바이스·채널과 제품-채널 연결을 관리합니다.
- 회원 메뉴의 `사용자 설정` 다음에 있는 `레벨 권한`에서 업무별 최소 레벨을 변경합니다. 이 페이지의 최초 최소값은 20이며, 현재 접근 권한이 있는 사용자는 이 페이지 자체의 최소 레벨도 조정할 수 있습니다. 위 숫자는 초기 기본값이며 실제 접근과 메뉴·버튼은 저장된 정책을 따릅니다.
- 디바이스는 WebSocket으로 서버에 연결되며, 채널 상태와 명령 결과를 웹 화면에 전달합니다.
- 제품-채널 연결을 설정하면 해당 채널이 실제 `ON` 상태 변경으로 처리될 때 연결 제품의 누적 수량과 작업 수량을 각각 1 증가시킵니다. 목표 수량은 변경하지 않습니다. 연결된 제품은 각각 증가하며, 반복되는 동일 상태 보고만으로는 보통 다시 증가하지 않습니다.
- 디바이스·채널 표시 상태는 `Visible` 또는 `Invisible`이고, 디바이스 동작 상태는 Enabled/Disabled로 관리합니다. Device 관리에서 Disabled로 바꾸면 Invisible도 함께 적용되고, Enabled로 복구하면 Visible로 돌아옵니다. Visible/Invisible만 별도로 바꾸면 Enabled/Disabled 상태는 변하지 않습니다. Invisible 디바이스·채널과 Disabled 디바이스는 일반 Device 보기·제어 화면에서 숨겨집니다. Disabled 디바이스는 서버 소켓 연결과 명령 전달이 중지되지만 예약·제품 연결 관리에서는 선택할 수 있습니다.
- 개인 설정은 회원별로 저장됩니다. 테마와 일부 보기 설정은 화면에 적용되며, 표시 항목을 숨겨도 서버 데이터나 제어 동작은 변경되지 않습니다.
- 디바이스 메뉴의 `사용자 디자인`(`/user_customization.html`)에서 전체 장치·채널 중 개인 채널을 선택하고 순서를 저장할 수 있습니다. 각 채널의 `디자인` 선택 목록에서 01~08 중 하나를 지정할 수 있으며, 기본은 기존 디자인 01입니다. 07은 금속 회전 스위치, 08은 OFF일 때 배경과 구별되는 밝은 회색·왼쪽, ON일 때 초록·오른쪽으로 표시되는 135×45px 슬라이드입니다. 한 버튼으로 현재 OS 상태의 반대 상태를 요청하며, 실제 장치 상태가 수신된 뒤 ON/OFF와 색상·스위치 이미지가 변경됩니다.
- 사용자 디자인의 디바이스 드롭다운과 전체 보기에는 `device.is_visible=1`인 장치만 표시합니다. 스위치·램프·그래프의 채널 선택 및 저장된 카드·팝업은 해당 장치의 `device_channel.is_active=1`인 채널만 표시하며, 스위치는 추가로 `web_control_enabled=1`이어야 합니다. 숨겨진 채널의 개인 디자인·선택·순서는 삭제하지 않으며 다시 표시 가능해지면 복원합니다. OFF 상태에서 ON으로 전환하려면 `web_on_enabled=1`, ON 상태에서 OFF로 전환하려면 `web_off_enabled=1`이어야 하며, 금지된 방향은 버튼을 비활성화합니다. 서버도 웹 명령을 저장·전달하기 전에 표시·활성·제어 및 방향별 허용을 검사합니다. 예약 명령의 기존 정책은 유지합니다. 관리 변경은 다음 사용자 디자인 조회(주기적 갱신·창 재포커스)에 반영되며 서버 변경 적용에는 재시작이 필요합니다.

- 버튼 04는 사진 대신 입체적인 벡터로 표현한 레버형 토글입니다. 금속 반사광이 있는 둥근 손잡이·가는 축·볼 관절과 음영이 있는 작은 원형 받침으로 구성하고, 나사산·단자·큰 본체는 생략해 레버를 강조합니다. 실제 OS 상태에 따라 레버가 OFF 왼쪽/ON 오른쪽으로 200ms 동안 기울어지며, 카드와 선택 창 미리보기에 동일하게 적용됩니다. 동작 줄이기 설정에서는 즉시 전환합니다. 기존 04 선택과 제어 동작은 유지됩니다.
- 사용자 디자인의 채널 하단에는 일시적인 명령 처리·서버 연결 확인 문구 대신 장치 연결 상태를 유지합니다. 처리 중·재연결 중 제어 차단과 오류 안내는 그대로 유지됩니다.
- 사용자 디자인은 명령 대기 중 밝기·그림자를 유지하고, 실제 ON/OFF 상태가 수신되면 배경색을 100ms 동안 부드럽게 전환합니다(동작 줄이기 설정에서는 즉시 전환). 상단 요청·저장 완료 안내 줄은 표시하지 않으며, 오류·응답 지연은 버튼 목록 아래에 표시합니다.
- 채널 선택 창 제목 옆의 `스위치`·`램프`·`그래프` 링크로 표시할 섹션을 전환합니다. 전환 시 다른 섹션의 선택과 검색어는 유지되며, 전체 선택·선택 해제는 현재 섹션의 검색 결과에만 적용됩니다. 동일 채널을 각 섹션에서 별도로 선택·저장할 수 있으며 카드 순서도 각각 이동할 수 있습니다. 검색창 앞의 디바이스 드롭다운(맨 위 `전체 디바이스`)으로 표시 범위를 정하면 `장치 또는 채널 검색`은 선택한 디바이스 안에서만 검색합니다. 스위치·램프·그래프 섹션에 공통으로 적용되며, 전체 선택·선택 해제도 디바이스와 검색으로 걸러진 결과에만 적용됩니다. 선택 창을 다시 열면 `전체 디바이스`와 빈 검색어로 초기화됩니다. 스위치 유형은 내부적으로 `switch`, 디자인 키는 `switch_design`을 사용합니다(유형 생략 시에도 스위치). 기존 `button` 유형·`button_design` 저장 정보와 구버전 저장 요청은 스위치 형식으로 변환되며 디자인·채널 설정·순서는 유지됩니다. 다음 조회 시 저장 데이터도 갱신하며 새 API를 적용하려면 서버 재시작이 필요합니다. HTML의 실제 조작 요소는 표준 `<button>`을 유지합니다.
- 램프는 OS 상태를 표시하는 읽기 전용 카드입니다(ON 빨강, OFF 회색, 미확인 상태는 빗금과 `-`). 01 입체 원형 표시등·02 경광등·03 실린더 전진/후진·04 도어 열림/닫힘·05 백열전구·06 모터·07 배관 수도꼭지·08 회전 팬을 지원합니다. 01은 은색 테두리와 광택·음영을 적용한 원형 표시등입니다. 경광등은 ON일 때 방사형 빛만 1.5초 주기로 부드럽게 점멸하며 본체·문구는 고정됩니다. OFF 또는 동작 줄이기 설정에서는 점멸하지 않습니다. 실린더와 모터는 디자인 영역의 가로·세로 80% 크기로 표시하며 실린더는 ON일 때 전진, OFF일 때 후진 이미지입니다. 모터 회전부와 팬은 ON일 때만 회전하며 동작 줄이기 설정에서는 정지합니다. 도어는 ON일 때 열림, OFF일 때 닫힘 이미지입니다. 버튼과 동일한 카드 크기·상단 이름을 사용하며 램프 영역은 하단까지 확장되고 연결 상태·이동 버튼이 그 위에 표시됩니다. 그래프도 선택·저장·순서 이동할 수 있습니다.
- 그래프 01은 램프 18과 같은 둥근 화살촉·테두리·5개 꼬리를 사용하는 IStr 회전 화살표입니다. 위쪽 0°·오른쪽 90°·아래쪽 180°·왼쪽 270°이며 양수·0·음수 정수를 지원합니다. 각도를 360으로 나누어 환산하지 않아 값 증가 시 시계방향, 감소 시 반시계방향으로 회전하고 720°는 두 바퀴를 의미합니다. 초기 위쪽 자세 또는 현재 표시 각도에서 새 목표로 800ms 동안 부드럽게 이동하며 회전 중 새 값이 오면 현재 표시 위치에서 이어갑니다. OS ON은 빨강, OFF는 회색, 미확인은 회색 빗금이며 IS 상태와 무관합니다. IStr가 비어 있거나 정수가 아니거나 JavaScript 안전 정수 범위를 벗어나면 마지막 유효 방향을 유지하며 정수 각도 입력 안내를 표시합니다. 카드·선택 창 미리보기는 같은 값과 색상을 사용하며 동작 줄이기 설정에서는 각도를 즉시 반영합니다. 기존에 저장한 그래프 채널에도 자동 적용됩니다.
- 그래프 01의 회전 범위 바깥에는 고정 원형 외곽선과 안쪽으로 향하는 짧은 눈금을 표시합니다. 위쪽 0°부터 시계방향으로 10°마다 주 눈금 36개, 그 사이 5°마다 더 짧고 가는 보조 눈금 36개를 배치합니다. 원 안쪽에는 위 0°·오른쪽 90°·아래 180°·왼쪽 270°를 눈금 끝과 여백을 두고 표시합니다. 외곽선·눈금·각도 숫자는 화살표와 함께 회전하거나 OS에 따라 색이 바뀌지 않으며 카드와 미리보기에 동일하게 표시됩니다. 그래프 카드도 버튼·램프와 같은 공통 카드 폭을 사용하며, 내용 영역은 램프와 동일한 120px 높이와 하단 연결 상태·이동 버튼 배치를 사용합니다. 원형 눈금과 화살표는 이 영역을 벗어나지 않는 최대 크기로 표시합니다. 미리보기는 선택 창에 맞는 작은 크기를 유지합니다.
- 램프 내부 상단에는 버튼과 같은 위치에 디바이스 ID(왼쪽)와 OS 번호(오른쪽)를 표시하며, ON/OFF는 램프 중앙에 표시합니다. ID·OS 번호·연결 상태는 배경색 없이 공통 짙은 파란색 글자와 밝은 그림자를 사용합니다.
- 모든 램프·그래프의 IStr 원문은 버튼의 IStr와 동일하게 카드 내용 영역의 왼쪽 하단(연결 상태 위)에 표시합니다. 왼쪽 여백·세로 위치·표시 폭·글자 크기를 버튼과 맞추며, 그래프의 별도 각도 표시는 유지합니다. 문자열은 OS 상태와 독립적으로 실시간 갱신되며, 긴 문자열은 말줄임하고 툴팁에서 전체 내용을 확인할 수 있습니다. 버튼의 IS 상태 표시는 유지됩니다.
- 모든 버튼·램프·그래프 디자인의 채널 이동 버튼은 가로 36px·세로 18px로 표시합니다. 기존 대비 높이만 절반으로 줄이며 카드·하단 영역 크기와 드래그·키보드 순서 이동 동작은 유지합니다.
- 모든 채널의 이동 버튼은 왼쪽 하단, 같은 크기(36×18px)의 `⚙ 채널 설정` 버튼은 오른쪽 하단에 고정합니다. 설정 창은 `기본 옵션`과 `디자인 설정`으로 구분하며 입력란의 패딩은 공통 6px입니다. 이름 변경 입력란 다음의 체크박스는 디바이스 이름 숨기기 → 채널 이름 숨기기 → 디바이스 ID 숨기기 → 채널 ID 숨기기 → IS State 숨기기 → IStr 숨기기 → 팝업 하기 → 채널 제거하기 순입니다. 각 옵션은 스위치·램프·그래프에 공통 적용되며 제어·실시간 갱신·연결 끊김 표시는 유지됩니다.

- 26·27번 회전 화살표는 곡선 몸통과 꼬리를 두껍게 하고 화살촉 꼭짓점을 곡선으로 처리합니다. 꼬리의 곡선 길이를 줄여 이웃 화살표와 테두리까지 닿지 않도록 간격을 둡니다. 각 화살표에 짙은 테두리를 유지하며 빨강/회색 순차 점등으로 방향을 표시합니다.

## 회원 등급과 권한

회원 `permission_level`은 1~25입니다. 1~20은 업무별 최소 레벨 정책을 따르며 기존 권한 경계를 유지합니다. 21~25 프로그래머는 사이트별 레벨 권한에 별도로 표시하지 않고 모든 사이트와 기능에 접근합니다. 레벨 권한 화면은 계속 1~20까지만 설정합니다.

| 등급 | 업무 권한 | 회원 관리 범위 |
| ---: | --- | --- |
| 1~7 | 생산 현황·디바이스 보기·개인 사용자 디자인·회원정보·개인 설정 | 회원 관리 기능 없음 |
| 8~11 | 위 업무 + 디바이스 수동 출력 제어 | 회원 관리 기능 없음 |
| 12~13 | 위 업무 + 생산 입력·생산 리포트 | 회원 관리 기능 없음 |
| 14~15 | 위 업무 + 제품 관리·디바이스 예약 | 회원 관리 기능 없음 |
| 16~19 | 위 업무 + 회사 조직·회원·디바이스·채널·제품-채널 연결 관리·디바이스 리포트 | 본인보다 낮은 레벨의 회원 관리, 본인 레벨까지 부여 가능 |
| 20 | 기존 전체 업무와 레벨 권한 정책 편집 | 1~19레벨 회원 관리, 최대 20레벨 부여 가능 |
| 21~25 | 모든 사이트·기능 접근, 프로그래머 | 자신보다 낮은 레벨만 관리하며, 새로 부여할 수 있는 최대 레벨은 자신의 레벨보다 1 낮음 |

프로그래머 계정은 `company_organization.group_code='ZZZ'`에 소속되어야 합니다. 서버 시작 시 `ZZZ/NULL/NULL/NULL/NULL` 조직을 준비하며, `MASTER` 계정은 permission_level 25와 이 조직을 사용합니다. 그룹 코드는 `ZZZ`이고 회사·사업장·부서·직무 코드는 문자열이 아닌 SQL `NULL`입니다. 기존 MASTER 계정도 서버 시작 시 이 조직으로 연결하며 다른 회원의 조직은 변경하지 않습니다. `MASTER`는 프로그래머 계층보다 상위인 시스템 관리자라 최초 21~25레벨 프로그래머를 지정할 수 있습니다. 일반 레벨 20 계정은 프로그래머 등급을 부여할 수 없습니다.

### 레벨 권한 정책

`/user-level.html`의 가로축은 1~20이고 막대는 해당 업무를 이용할 수 있는 레벨 구간입니다. 현재 이 페이지의 접근 기준을 만족하는 사용자는 슬라이더 또는 `User-level` 숫자를 조정한 뒤 저장합니다. `레벨 권한` 행도 1~20 범위로 변경할 수 있습니다. 다른 사용자의 변경과 충돌하면 저장을 거부하므로 다시 불러와 확인합니다. 회원정보는 로그인 사용자 접근으로 고정해 계정 복구 차단을 방지합니다.

이 페이지의 기준을 낮추면 해당 레벨의 사용자도 전체 업무 권한을 편집할 수 있습니다. 자신의 레벨보다 높게 올려 저장하면 그 이후 링크·페이지·조회 및 수정 API는 새로운 기준에 따라 차단됩니다. 현재 DB에 저장된 최소값은 기능 변경만으로 자동 하향하지 않습니다.

`site_permission_policy`는 사이트당 한 행이며 컬럼 순서는 `poicy_id`(기본키), `site_name`(페이지 경로), `default_leble`(최초 기본 레벨), `permisson_lebel`(현재 최소 레벨), `updated_by`(마지막 수정자 ID), `updated_at`(마지막 수정 시각)입니다. 예를 들어 `/device-control.html` 행의 `permisson_lebel`이 8이면 해당 페이지와 제어 권한은 8레벨부터 허용됩니다. 저장 API는 수정된 사이트의 현재 레벨과 감사 정보만 갱신하고 기본값은 변경하지 않습니다.

페이지의 `기본값` 버튼은 코드 상수가 아니라 조회한 사이트 행의 `default_leble`을 편집 화면에 불러옵니다. 이때 바로 저장하거나 운영 권한을 변경하지 않으며 `저장` 후에만 적용됩니다. 신규 생성 시 기본값과 현재 레벨을 같은 초기값으로 저장합니다. 기존 5열 테이블에는 세 번째 위치에 기본값 열을 추가하고 최초 배포 기본 레벨을 한 번 채우며, 현재 사용자 지정 레벨과 수정자·수정 시각은 보존합니다. 이미 보관된 기본값은 재시작해도 덮어쓰지 않습니다.

기존 JSON 정책 테이블은 설정값·수정자·수정 시각을 보존해 새 행 구조로 이전하고, 기존 원본은 `site_permission_policy_legacy`로 남깁니다. 이미 20단계인 회원 레벨은 변경하지 않습니다. 구형 테이블에 명시적인 `scheme_version=10` 기록이 있는 경우에만 회원 1레벨은 유지하고 나머지 기존 레벨을 두 배로 한 번 변환합니다. 새 행 구조로 전환한 뒤 재시작해도 회원 레벨을 다시 변환하지 않습니다. 적용 전 DB를 백업하세요. 새 SQL 설치는 처음부터 사이트별 20단계 정책 행을 준비합니다.

서버 접근 제한은 저장 직후 적용됩니다. 실시간 연결 화면은 변경 알림으로 메뉴·버튼을 갱신하고, 나머지 화면도 포커스 복귀 또는 최대 15초 주기의 권한 조회로 갱신됩니다. 회원 레벨을 바꾸면 해당 회원의 기존 소켓은 재인증하도록 종료됩니다. 정책 변경은 채널 자체의 ON/OFF·조회 전용 활성화 제한을 우회하지 않습니다.

### 계정 상태와 승인

일반 업무 페이지와 API는 로그인, 계정 상태, 승인 여부와 기능별 최소 등급을 검사합니다. 생산 현황과 디바이스 상태 조회는 승인된 계정의 기본 기능이며, 회원정보는 로그인한 사용자가, 개인 설정은 정지되지 않은 계정이 이용할 수 있습니다. 신규 가입은 1등급 `PENDING`으로 시작하고, 관리자가 승인하면 1등급 `APPROVED` 계정이 됩니다.

16레벨 이상은 승인 전에도 권한에 맞는 업무를 이용할 수 있지만, 정지 계정은 레벨과 관계없이 업무 기능이 차단됩니다. 승인 예외도 업무별 최소 레벨을 우회하지 않습니다.

### 회원 관리 규칙

회원 관리는 기본 16레벨 이상이며 정책으로 조정할 수 있습니다. 관리자는 본인보다 낮은 레벨의 회원만 수정·승인·정지·삭제하고, 본인 레벨까지 부여할 수 있습니다. 본인 레벨 변경과 본인 계정 삭제는 허용되지 않습니다. 신규 승인 회원은 1레벨이며, 회원 수정에서 1~20 범위 내 관리자의 레벨 이하로 지정합니다.

메뉴와 버튼의 표시·활성화는 서버가 반환한 동일한 업무 권한을 사용합니다. 최종 접근 제한은 서버가 로그인·계정 상태·승인 여부·현재 레벨과 저장된 최소 레벨을 다시 검사합니다.

## 운영 흐름

### 최초 관리자와 회원

1. 서버와 DB를 준비하고 `MASTER_USERNAME`, `MASTER_PASSWORD`를 설정합니다.
2. 서버가 최초 관리자 계정을 생성합니다. 최초 계정은 승인된 25레벨 MASTER이며 조직 코드는 `ZZZ/NULL/NULL/NULL/NULL`입니다.
3. 사용자는 회원가입을 신청하고, 관리자는 회원 관리 화면에서 승인과 등급을 설정합니다. 최초 `MASTER` 계정은 레벨25와 ZZZ 조직으로 준비됩니다.
4. 실제 업무에 필요한 최소 등급만 부여합니다.

### 가입 조직과 신청·반려 이력

조직 기준은 `company_organization` 테이블입니다. `group_code`, `company`, `site`, `department`, `job`은 각각 `CHAR(3)`입니다. 일반 개인 사용자가 아닌 조직은 그룹·회사·사업장·부서·직무의 5단계로 등록하고 관리합니다. 코드는 문자·숫자 3자리로 입력하고 영문은 대문자로 정규화합니다. 표시 이름은 각 코드에 대응하는 이름 컬럼에 저장합니다.

기존 DB는 서버 시작 시 `group` → `group_code`, `role` → `job`, `role_name` → `job_name`으로 컬럼명만 변경합니다. 기존 값·컬럼 자료형·조직 ID·회원 연결을 유지하며, 이미 변경된 컬럼은 다시 변경하지 않습니다. 같은 항목의 이전·새 컬럼이 동시에 있으면 임의 병합하지 않고 초기화를 중단합니다. 기존 화면과의 호환성을 위해 조직 API의 `group`·`role`·`role_name` 키는 SQL 별칭으로 유지합니다. 계정 권한인 `user_profile.role`은 변경하지 않습니다.

가입자는 일반 개인 사용자가 아닌 경우 그룹·회사·사업장·부서·직무 코드를 입력하고 `조직 확인`을 눌러 활성 5단계 조직과 매칭합니다. 조직 단계가 없는 경우 해당 코드는 비워 둘 수 있습니다. 일반 개인 사용자는 그룹·회사·사업장 코드가 `001/001/001`로 고정되고 부서·직무 코드를 가입 시 무작위 생성합니다. 개인별 두 코드 조합은 `user_profile`의 고유 인덱스로 중복되지 않게 저장하며, 발급 코드는 가입 완료 메시지와 회원 정보에 표시됩니다. 조직 정보를 모르면 `조직 정보 미확인 (Default)`를 사용합니다. 개인 사용자 기준 조직은 `001/001/001/NULL/NULL`이며 서버 시작 시 준비됩니다. 기존 개인 조직 회원 연결은 유지하고 회원별 부서·직무 코드를 보완합니다. 일반 개인 사용자가 아닌 회원은 가입 시 선택한 조직의 부서·직무 코드를 사용합니다. 회원 프로필은 회사 이름 스냅샷을 저장하지 않고 조직 ID를 참조하며, 개인별 코드는 일반 개인 회원에만 저장합니다. 조직 정보가 없는 기존 회원은 관리자가 회원 수정에서 조직을 연결할 수 있습니다.

회원 메뉴의 `레벨 권한` 다음에 있는 [회사 등록](public/user-company.html)에서 그룹 코드와 명칭은 필수입니다. 회사·사업장·부서·직무는 각각 코드와 이름을 함께 입력하거나 둘 다 비워 둘 수 있으며, 생략한 단계는 SQL `NULL`로 저장합니다. 기존 `DEF`·`미지정` 데이터는 자동 변환하지 않습니다. 서버 시작 시 기존 하위 코드·명칭 열을 데이터와 길이를 유지한 채 `NULL` 허용으로 보완합니다. 입력한 코드가 기존 코드와 같으면 해당 명칭이 자동으로 채워지며, 같은 상위 조직 아래 다른 코드가 이미 쓰는 명칭은 등록할 수 없습니다. 새 코드는 `미지정` 명칭을 사용할 수 없습니다. 기본 접근 레벨은 16이며 `레벨 권한`에서 조정할 수 있습니다. 등록 즉시 활성 조직은 회원가입의 5단계 조직 확인에 사용됩니다. 회원 관리의 승인 대기·전체 회원 표에는 그룹·회사·사업장과 회원의 부서·직무 코드가 표시됩니다. 회원 수정에서는 조직 ID를 선택합니다. 기존 DB에서 현재 조직과 일치하지 않는 legacy `region`·`company`·`position` 값은 `user_profile_organization_legacy`에 보관하고 `user_profile` 컬럼은 제거합니다. 목록은 조직·상태 열별 값 필터와 전체 검색을 제공합니다.

등록 후 코드는 변경할 수 없으며 다른 조합은 새로 등록합니다. 회원과의 연결을 보존하기 위해 삭제는 제공하지 않고 사용 중지로 관리합니다. 사용 중지는 이후 가입 조직 매칭만 차단하며 기존 회원의 계정 상태를 바꾸지 않습니다. 명칭을 수정해도 기존 회원정보에 저장된 회사·지역·직무는 소급 변경하지 않습니다. 기본 `DEF` 조직은 화면과 API에서 수정·사용 중지를 차단합니다.

기존 사이트 권한 테이블에는 회사 등록 행만 기본값·현재 레벨 16으로 추가하며 기존 사이트의 사용자 지정 레벨·기본값·감사 정보는 보존합니다. SQL로 직접 등록할 수도 있습니다. 예:

```sql
INSERT INTO company_organization
    (group_code,company,site,group_name,company_name,site_name)
VALUES
    ('GRP','COM','ST1','그룹명','회사명','사업장명');
```

가입 신청은 서버가 일반 조직의 5단계 코드 조합을 다시 조회하고 DB 표시 이름으로 조직 정보를 확정합니다. 브라우저에서 회사·조직 ID·권한값을 바꿔 전송해도 신뢰하지 않습니다. 일반 개인 사용자의 무작위 부서·직무 코드는 계정 권한인 `user_profile.role`·`permission_level`과 무관하며, 가입자는 기존처럼 USER·1레벨·PENDING으로 등록됩니다. 개인 사용자 기본 조직은 삭제하거나 비활성화하지 마세요.

회원 전화번호와 이메일은 각각 별도의 UNIQUE 컬럼이며 여러 회원의 `NULL`은 허용됩니다. 가입·회원정보 수정·관리자 회원 수정은 서버에서 두 값의 중복을 확인하고, 가입 시 검증 오류는 신청 버튼 오른쪽에 표시합니다. 기존 DB는 빈 연락처를 `NULL`로 정규화하고 전화번호 중복 그룹에서 회원 ID가 가장 낮은 계정의 번호를 보존하며 나머지는 `NULL` 처리한 뒤 고유 인덱스를 적용합니다.

주소는 선택 입력이며 `user_profile.address VARCHAR(255) NULL`에 저장합니다. 가입 신청, 회원정보 수정, 관리자 회원 수정에서 주소를 조회·저장하며, 기존 DB는 서버 시작 시 주소 컬럼을 데이터 변경 없이 추가합니다.

가입 화면 이메일 아래의 신청 이유는 필수이며 앞뒤 공백을 제거한 1~2000자를 입력해야 합니다. 반려 후 재신청할 때도 회원정보 화면에서 `재신청 이유`를 입력하며, APPLICATION/REAPPLICATION 행을 `user_register_comment`에 저장합니다. `PENDING` 또는 `REJECTED` 상태의 신청자는 회원정보 화면에서 가입 신청을 취소할 수 있으며, 트랜잭션으로 회원 프로필과 연결된 설정을 삭제하고 취소 STATUS 이력을 남깁니다. 신청 이력은 append-only로 보존되며 회원 ID 연결만 NULL이 됩니다. 승인 권한이 있는 사용자가 회원 관리에서 반려할 때는 1~2000자의 반려 사유가 필요하며 REJECTION 행이 추가됩니다. 승인·정지 등 처리도 별도 이벤트로 남깁니다. 이력은 사용자 ID·당시 로그인 ID·이벤트 유형·코멘트·처리자 ID/로그인 ID·시각을 보관하고 기존 행을 덮어쓰지 않습니다. 가입과 신청 이력, 상태 변경과 처리 이력은 각각 같은 트랜잭션에서 저장됩니다.

승인된 회원은 회원정보 화면의 `관리자 요청`에서 `등급변경`, `조직 변경`, `탈퇴 신청`을 선택하고 1~2000자의 요청 내용 또는 탈퇴 사유를 입력합니다. `POST /api/me/change-request`는 DB의 현재 승인 상태를 확인하고 `user_register_comment`의 `event_type`에 LEVEL_CHANGE_REQUEST, ORGANIZATION_CHANGE_REQUEST 또는 WITHDRAWAL_REQUEST, `comment`에 내용을 추가합니다. 등급·조직 요청은 현재 등급·조직·승인 상태를 바꾸지 않으며 실제 수정은 기존 회원 관리 기능으로 별도 처리합니다. 탈퇴 신청은 확인 후 WITHDRAWAL_PENDING 전환과 사유 저장을 같은 트랜잭션에서 처리하고, 기존 탈퇴 취소 기능을 유지합니다. 서버 시작 시 기존 이력을 보존하면서 enum에 새 요청 유형을 추가합니다.

회원 관리의 승인·반려·정지·승인대기 변경·탈퇴 반려·탈퇴 승인·삭제는 모두 공통 코멘트 창을 사용합니다. 가입 반려 사유는 필수이며 나머지 처리 코멘트는 선택 입력(최대 2000자)입니다. 탈퇴 반려는 WITHDRAWAL_REJECTION, 탈퇴 승인은 WITHDRAWAL_APPROVAL, 일반 회원 삭제는 DELETION으로 구분합니다. 삭제 API는 JSON의 `action`(DELETE 또는 WITHDRAWAL_APPROVAL)과 `comment`를 받으며, 대상과 처리자를 확인하고 이력 추가와 회원 삭제를 같은 트랜잭션에서 처리합니다. 삭제된 회원의 신청 이력은 로그인 ID·처리자·코멘트를 유지하고 회원 ID 연결만 NULL로 보존합니다.

`승인 신청 대기자`에는 가입·탈퇴 신청뿐 아니라 승인 회원의 미처리 등급·조직 변경 요청도 요청별 행으로 표시됩니다. `pending_requests`가 회원 목록 응답에 포함되며, 요청 내용과 신청일을 확인할 수 있습니다. 등급·조직 요청은 기존 회원 승인 상태나 이용 권한을 낮추지 않습니다. 실제 등급·조직 수정은 기존 수정 기능으로 처리하고, 요청별 승인·반려는 `PUT /api/admin/users/:id/requests/:requestId`로 처리합니다. 응답 이력의 nullable `request_comment_id`로 원래 요청을 연결해 기존 이력을 덮어쓰지 않고 처리된 요청만 대기 목록에서 제외하며, 중복 처리·자기 요청 처리·동급 이상 회원 요청 처리를 차단합니다.

신청 처리 버튼을 누르면 동일 팝업에서 신청 이력과 현재 요청 내용을 확인하고 처리별 코멘트를 입력합니다. 이력 로딩 실패 시 제출은 비활성화되며 취소는 가능합니다. 가입·변경 요청 반려 사유는 필수이고 승인 코멘트는 선택입니다.

SQL 조회 예:

```sql
SELECT * FROM user_register_comment;
```

기존 `register_comment` 또는 `user-register_comment` 테이블은 서버 시작 시 `user_register_comment`로 이름만 변경해 이력을 보존합니다. 구형 테이블과 새 테이블이 동시에 존재하면 자동 병합하지 않고 중단하므로 데이터를 확인해야 합니다.

관리자는 회원 관리의 `신청 이력`, 신청자는 회원정보의 `신청 이력`에서 기록을 확인합니다. 본인 이력은 로그인한 본인만, 관리 이력은 회원 관리 권한으로 조회합니다. 회원이 삭제되어도 이력의 로그인 ID·코멘트는 남으며 연결 ID만 NULL이 됩니다. 코멘트에는 비밀번호나 장치 토큰 같은 비밀값을 적지 마세요.

### 제품 수량과 상태

1. 제품 관리 권한(기본 14레벨)으로 제품 코드와 누적·작업·목표 수량을 등록·수정합니다. 각 수량은 별도로 설정할 수 있습니다.
2. 생산 입력 권한(기본 12레벨)으로 작업 수량 증감과 작업 내용을 입력합니다. 증감은 누적·작업 수량에 함께 반영되며 0 미만이나 정수 최대값을 넘는 변경은 저장되지 않습니다.
3. 생산 현황에서 업데이트된 값을 확인합니다.

제품 상태는 `대기`, `생산중`, `수리중`, `완료`, `정지`를 사용합니다. 생산 입력 화면에서 상태를 변경할 수 있으며, 이전·신규 상태가 `product_quantity_history`에 함께 기록됩니다.

누적 수량은 기존 `product.quantity`를 그대로 사용하고, 작업 수량은 `product.work_quantity`, 목표 수량은 `product.target_quantity`로 보관합니다. 기존 DB 최초 적용 시 누적 수량은 보존하고 작업 수량을 현재 누적 수량과 같게 초기화하며, 이후 서버 재시작 때는 작업 수량을 다시 초기화하지 않습니다. 새 제품은 두 수량을 별도로 입력합니다.

누적·작업·목표 수량 변경과 제품 상태 변경은 `product_quantity_history`에 기록합니다. 이력에는 변경 시점의 수량 스냅샷, 이전·신규 제품 상태, 변경 사유·유형·사용자와 KST 시각이 포함됩니다. 수량 변경 트리거는 같은 트랜잭션에서 이력을 저장합니다. 이전 수량이나 상태는 과거 행에 소급해 만들어 넣지 않습니다. Device 생산 이력은 변경 사용자에 Device ID를 기록하고 사유는 비워 둡니다. 수동 생산 입력은 입력한 양·음수 증감량을 누적·작업 수량에 동시에 반영합니다.

### 제품과 채널 연결

1. 제품-채널 연결 권한(기본 16레벨)으로 `/product-channel-link.html`에 접속합니다.
2. 제품, 디바이스, 해당 디바이스의 채널을 선택해 연결을 등록합니다.
3. 현재 연결 목록에서 연결을 수정하거나 삭제할 수 있습니다.
4. 연결된 채널의 `ON` 처리 시 연결 제품의 현재 수량이 증가하는지 생산 현황에서 확인합니다.

한 채널에 여러 제품을 연결하면 그 채널의 `ON` 처리마다 사용 설정된(`product.is_enabled=1`) 연결 제품의 누적·작업 수량이 증가합니다. 사용 중지 제품은 생산 현황과 Device 자동 증가에서 제외되지만 제품-채널 연결 정보는 유지됩니다. 같은 제품·디바이스·채널 조합은 중복 등록할 수 없습니다. Invisible 디바이스·채널 여부와 제품 사용 여부는 별도 설정이며, Disabled 디바이스는 소켓 메시지를 보내지 않으므로 자동 증가가 멈춥니다.

디바이스 리포트와 예약 관리의 디바이스 선택에는 `device.is_enabled=1`인 장치만 표시합니다. 제품-채널 연결 등록·수정에서도 사용 중인 디바이스와 `product.is_enabled=1`인 제품만 선택할 수 있으며 서버가 저장 시 다시 검사합니다. 기존 비활성 장치의 예약과 비활성 제품·장치의 연결 정보는 목록에 유지됩니다. `is_visible`에 따른 기존 표시 정책은 변경하지 않습니다.

### 개인 사용자 디자인

1. 디바이스 메뉴에서 `디바이스 제어` 아래의 `사용자 디자인`을 엽니다.
2. `채널 선택`에서 장치별 채널을 체크하고 저장합니다. 목록과 순서는 로그인 계정별로 DB에 저장됩니다.
3. 카드의 이동 손잡이를 드래그해 순서를 변경합니다. 손잡이에 키보드 초점을 둔 상태에서는 방향키로도 순서를 바꿀 수 있습니다.
4. ON은 `#b42318`, OFF는 `#525b66` 배경으로 표시됩니다. 버튼을 누르면 반대 상태를 요청합니다.

사용자 디자인과 출력 제어 권한은 각각 정책을 따릅니다. 출력 제어의 기본 최소값은 8레벨입니다. 장치가 Disabled이거나 채널이 조회 전용이면 제어할 수 없으며 다음 동작의 ON/OFF 활성화 값도 검사합니다. 서버 미연결·명령 처리 중에는 버튼이 비활성화됩니다. 선택 목록은 `user_setting.User_customization`에 저장되며 장치 오프라인 명령은 기존 큐 정책을 따릅니다.

사용자 디자인의 페이지 내부 식별자·공유 모듈·권한 키는 `User_customization` 계열이며 설정 API는 `GET/PUT /api/me/User_customization`입니다. 페이지와 전용 파일은 `public/user_customization.html`, `public/user_customization.js`, `public/user_customization_graph_config.js`, `public/user_customization_stream_chart.js`이며 차트 테스트는 `test/user_customization_stream_chart.test.js`입니다. 이전 `/device-simple.html` 주소는 권한 검사 후 새 `/user_customization.html` 주소로 이동합니다. 공통 CSS·이미지 경로는 유지합니다. 서버 재시작 시 기존 사이트 권한 행의 주소만 변경하여 ID·레벨·감사 정보를 보존하고, 기존 `simple_channels` 컬럼을 `User_customization`으로 이름을 바꾸어 설정을 보존합니다(두 컬럼이 이미 있으면 새 컬럼이 NULL인 행만 복사). 기존 `/api/me/simple-channels` API는 동일 권한 검사·저장 로직의 호환 주소로 유지하며, 과거 `device_simple` 권한 설정도 기존 레벨을 보존해 읽습니다. 변경 후 브라우저를 강력 새로고침(Ctrl+F5)하세요.

### 디바이스와 예약

디바이스 관리에서 장치를 등록하고 Visible/Invisible 표시와 Enabled/Disabled 동작 상태, 채널 이름을 관리합니다. Disabled로 설정하면 Invisible도 적용하고 기존 소켓을 닫아 새 연결을 거부합니다. 다시 Enabled로 바꾸면 Visible로 복구되어 장치가 재접속할 수 있습니다. 표시 상태만 별도로 변경해도 동작 상태는 유지됩니다. **명령 전송 성공과 장치가 실제 출력을 적용한 것은 다르므로**, 장치 응답과 보고된 현재 상태를 확인합니다.

예약은 기본 14레벨 이상이 조회·설정하며 정책으로 조정할 수 있습니다. 서버는 약 5초 간격으로 실행 시점을 확인합니다. Invisible/Disabled 장치와 Invisible·조회 전용 채널도 예약 대상으로 선택할 수 있습니다. Disabled 장치의 예약 명령은 큐에 보류되며 Enabled 복구 후 재접속하면 전달됩니다. 예약 활성 여부와 명령 처리 결과는 별도이며, 시간 기준은 한국 표준시(KST)입니다.

### 디바이스 채널 리포트

디바이스 리포트 권한(기본 16레벨)으로 [리포트 페이지](public/device-report.html)에 접속합니다.

- `분석 항목 선택`에서 통계 6개와 그래프 8종을 개별 선택할 수 있습니다. 그래프는 ON · OFF 상태, ON 누적 횟수, ON 누적 시간과 분별·시간별·일별·주간별·월별 ON 전환 횟수입니다. 기본은 전체 선택이며 최소 한 항목이 필요합니다. 선택 변경 후 리포트를 다시 조회하면 화면과 PDF에 선택한 항목만 포함됩니다.
- 기존 ON·OFF 횟수는 조회 기간 안에 실제 시간이 존재하는 연속 상태 구간의 수입니다. 조회 시작 시 이미 유지 중인 상태도 1회 포함하며, 같은 상태의 반복 기록은 추가로 세지 않습니다. ON 누적 횟수 그래프는 ON 구간 시작마다 증가하며 마지막 값은 ON 횟수 통계와 같습니다. 새 기간별 ON 전환 횟수 그래프는 실제 OFF→ON 변경만 집계하므로, 최초 관측 ON이나 조회 시작 시 이미 ON인 상태와 반복 ON 기록은 더하지 않습니다. 이력이 없는 구간은 확인 불가, 일부 이력만 있는 구간은 확인된 기록 합계로 구분합니다.
- 기간별 집계는 KST 기준 매분 00초, 정시, 자정, 월요일 00:00, 매월 1일 00:00, 매년 1월 1일 00:00 경계에 맞춥니다. 월·연간은 실제 달력과 윤년을 따르고 조회 시작·종료에 걸친 구간은 선택 범위만 집계합니다. 분별 구간은 선택 채널 전체 합계 100,000개까지이며 초과 시 기간·채널 수를 줄이거나 분별 항목을 해제합니다.
- 시간 기준은 한국 표준시(KST)이며 시작 시각은 포함하고 종료 시각은 포함하지 않습니다. 미래 기간은 조회할 수 없고, 한 번에 최대 366일·변경 이력 100,000건까지 조회합니다. 초과 시 기간을 줄여야 하며 데이터를 임의로 잘라 집계하지 않습니다.
- 그래프 X축은 그래프 주기에 맞는 눈금과 라벨을 사용합니다. 분별·시간별은 월·일과 시각, 일별은 일, 주간별은 월요일 시작, 월별은 년·월을 표시합니다. 화면과 PDF는 같은 기간 경계 규칙을 사용합니다.
- `채널 PDF 다운로드`는 해당 채널을, `디바이스 PDF 다운로드`는 조회 시 선택한 채널만 채널 단위로 묶어 `.pdf` 파일로 직접 내려받습니다. 그래프가 많으면 그래프 제목 경계에서 페이지를 나눠 읽기 쉬운 크기를 유지하고 페이지별 장치·채널 코드를 표시합니다. 인쇄 창을 열지 않으며 PDF에는 한글, 그래프와 통계가 포함됩니다.
- `Excel 다운로드`는 조회 시 선택한 채널만 실제 `.xlsx` 파일로 내려받습니다. 채널 요약, 상태 구간, 상태 변경 이력과 시간별·일별·주간별·월별·연간별 ON 전환 횟수 시트를 포함하며, 분별 항목 선택 시 분별 시트도 추가됩니다. 기간별 시트는 횟수와 KST 시작·종료, 이력 확인 여부를 담습니다. 채널 선택을 바꾸면 리포트를 다시 조회한 뒤 다운로드합니다.
- 집계 기준은 저장된 **출력 상태**입니다. `총 전환 횟수`는 ON·OFF 구간 수의 합이 아니라 실제 상태 변경 횟수입니다. 같은 상태의 반복 보고나 상태가 바뀌지 않은 예약 완료 기록은 전환 횟수에서 제외합니다. 첫 관측 상태는 전환 횟수 없이 기준 이력으로 저장하지만, 이후 유지되는 상태 구간은 ON·OFF 횟수에 포함합니다. 통신이 끊겼을 때 실제 접점 상태는 검증할 수 없으므로 이 통계는 물리적 가동 시간을 보증하지 않습니다.
- 기존 장치별 1,000건 상태 이력 자동 삭제는 중단합니다. 이미 삭제되었거나 수집하지 않은 과거 상태는 복원할 수 없으며 `확인 불가`로 표시하고 ON/OFF 시간에 더하지 않습니다. 첫 관측 전 구간도 확인 불가입니다. 운영 시 DB 용량·백업 정책을 함께 관리하세요.

### 제품별 현황 리포트

생산 리포트 권한(기본 12레벨)으로 [생산 리포트 페이지](public/product-report.html)에 접속합니다. 리포트와 조회용 목록은 생산 리포트 정책, 제품 목록·등록·수정·삭제는 제품 관리 정책(기본 14레벨)을 따릅니다.

- 조회는 최대 50개 제품, KST 기준 시작 포함·종료 미포함, 최대 366일·이력 100,000건입니다. 제품 선택은 처음에 모두 미선택이며 분석 항목은 전체 선택입니다.
- 제품 선택 목록과 리포트 조회 대상에는 활성 제품만 포함됩니다. 비활성 제품은 선택하거나 조회할 수 없습니다.
- `분석 수량 기준`에서 누적 수량 또는 작업 수량을 선택합니다. 기본은 누적 수량입니다. 선택 기준은 초기·종료·증가 통계, 그래프, PDF, Excel에 동일하게 적용됩니다. 누적 기준은 `quantity`, 작업 기준은 별도 `work_quantity` 스냅샷을 사용합니다. 증가 수량은 종료와 초기의 차이이며 음수일 수 있습니다. 시간 구간별 작업량은 각 스냅샷의 양수 변화만 합산합니다.
- 초기 수량, 종료 수량, 증가 수량, 기준 수량 추이와 분별·시간별·일별·주간별·월별 작업 수량 그래프를 개별 선택할 수 있습니다. 분별은 매분, 시간별은 정시, 일별은 자정, 주간별은 월요일, 월별은 매월 1일 KST를 경계로 집계합니다. 분별 구간은 선택 제품 전체 합계 100,000개까지이며 초과 시 기간·제품 수를 줄이거나 분별 항목을 해제합니다.
- 제품별 PDF는 선택한 제품과 분석 항목만 포함하고 인쇄 창 없이 다운로드합니다. Excel에는 제품 요약, 선택된 기준의 수량 변경 이력, 제품 상태 변경 이력, 분별(선택 시)·시간별·일별·주간별·월별 작업 수량 시트를 포함합니다. 연간별 작업 수량 시트는 제공하지 않습니다.
- `product_quantity_history`와 제품 트리거는 수량 또는 상태 변경을 기록합니다. 상태 이력에는 변경 전·후 상태가 포함됩니다. 기존 행에 없던 상태 이력은 소급 생성하지 않으며, 서버 DB 계정에는 기존 권한 외에 `TRIGGER` 권한이 필요합니다.
- 누적·작업 수량의 기준 이력이 없으면 조회 기간의 첫 기록을 초기 기준으로 사용하고 Excel·화면에 이를 표시합니다. 수집 전 기간이나 자료가 없는 구간은 확인 불가로 구분합니다. 과거 데이터는 복원하지 않으므로 이력 테이블의 용량과 백업을 관리하세요.

## 설치와 실행

### 준비 사항

- Node.js와 npm
- MySQL 또는 MariaDB 데이터베이스
- 디바이스 펌웨어를 빌드할 경우 PlatformIO와 지원 보드 및 USB 드라이버

### 패키지 설치

프로젝트 루트에서 실행합니다.

```bash
npm install
```

### 데이터베이스 준비

서버의 `DB_NAME`은 **이미 존재하는 데이터베이스**를 가리켜야 합니다. 방법은 다음 중 하나를 선택합니다.

- 신규 `factory` DB: DB가 없는 상태에서 [schema.sql](schema.sql)을 한 번 실행합니다. 이 파일은 DB와 현재 테이블, 예시 제품 및 기본 디바이스·16개 채널을 생성합니다. `factory`가 이미 있으면 실행하지 마세요.
- 다른 이름의 빈 DB: DB를 먼저 생성하고 `DB_NAME`을 해당 이름으로 설정합니다. 서버가 필요한 테이블을 준비합니다. 예시 제품은 제품 관리 화면에서 등록합니다.
- 운영 중인 DB: 기존 DB를 백업하고 현재 스키마와 호환되는지 확인합니다. 서버 시작 시 `user_profile.username`을 `login_id`로, `device.device_id`를 `device.device_code`로 이전하고 관련 외래키를 복구합니다. `schema.sql`을 운영 DB에 재실행하거나, 구버전 테이블을 임의로 삭제하지 마세요.

서버는 테이블 준비와 제한된 호환 처리를 하지만 모든 과거 DB 구조를 자동 이전하지는 않습니다. 시작 로그에 스키마 오류가 있으면 기존 DB를 보존하고 백업·마이그레이션 계획을 확인하세요.

### 환경 파일 설정

프로젝트 루트에 `.env`를 만들고 환경에 맞게 설정합니다.

```dotenv
PORT=8080
DB_CLIENT=mysql
DB_HOST=localhost
DB_PORT=3306
DB_USER=factory_user
DB_PASSWORD=change_this_database_password
DB_NAME=factory
DB_POOL_SIZE=5

MASTER_USERNAME=master
MASTER_PASSWORD=choose_a_strong_master_password
MASTER_NAME=관리자

DEVICE_ID=DEVICE-D1-001
DEVICE_TOKEN=replace_with_random_device_token
```

DB 생성 권한이 필요한 신규 테이블 준비 단계에 충분한 권한을 부여합니다. DB 계정과 최초 관리자 비밀번호, 디바이스 토큰은 실제 값으로 바꾸고 저장소에 커밋하지 마세요.

### 서버 시작

```bash
npm start
```

기본 주소는 `http://localhost:8080`입니다. `PORT`를 바꾼 경우 해당 포트를 사용합니다. 서버는 DB 연결과 스키마 준비를 마친 뒤 요청을 받습니다. DB 초기화 실패 시 서버가 시작되지 않으므로 콘솔의 오류와 `DB_HOST`, `DB_PORT`, `DB_NAME`, 계정 권한을 확인하세요.

서버 세션은 프로세스 메모리에 저장되므로 서버를 재시작하면 사용자가 다시 로그인해야 합니다. DB의 제품·회원·디바이스 데이터는 정상 재시작으로 삭제되지 않습니다.

### Windows 전용 실행기

Node.js 22.12 이상과 Windows 10 이상이 필요합니다. 저장소에서 `npm install` 후, 위의 웹 서버를 먼저 실행하거나 실행 중인 서버의 주소를 준비합니다. 다른 PowerShell 창에서 다음 명령으로 접속합니다.

```powershell
npm run desktop
# 다른 PC의 서버 또는 다른 포트에 접속하는 경우
npm run desktop -- --url https://factory.example.com
```

기본 접속 주소는 `http://localhost:8080`입니다. 첫 실행 시 Electron 런타임 다운로드를 위해 인터넷 연결이 필요할 수 있습니다. 실행기 안에서 로그인하고 `사용자 디자인 → 채널 설정 → 팝업 하기 → 저장`을 사용합니다. 서버는 실행기가 자동으로 시작하지 않으며 기존 DB·로그인·권한 정책을 그대로 사용합니다. 서버 접속 실패 시 오류 창을 표시합니다.

실행기는 지정한 서버와 같은 출처의 페이지로만 이동할 수 있습니다. 채널 팝업은 사용자 디자인 페이지에서만 생성하며, 팝업 안의 페이지 이동과 추가 창 생성은 차단합니다. 웹 콘텐츠에 Node.js·파일 시스템 접근 권한을 노출하지 않습니다. 신뢰하는 서버 주소만 지정하고 원격 접속에는 HTTPS를 사용하세요. 설치형 배포 파일은 포함하지 않으며 위 명령으로 실행합니다.

## 환경 설정

| 변수 | 기본값 | 설명 |
| --- | --- | --- |
| `PORT` | `8080` | 웹 서버 포트 |
| `DB_CLIENT` | `mysql` | `mysql` 또는 `mariadb` |
| `DB_HOST` | `localhost` | DB 호스트 |
| `DB_PORT` | `3306` | DB 포트 |
| `DB_USER` | `root` | DB 사용자 |
| `DB_PASSWORD` | 빈 문자열 | DB 비밀번호 |
| `DB_NAME` | `factory` | 미리 생성해 둔 DB 이름 |
| `DB_POOL_SIZE` | `5` | DB 연결 풀 크기 |
| `MASTER_USERNAME` | 없음 | 최초 관리자 아이디. 설정 시 관리자 계정을 준비 |
| `MASTER_PASSWORD` | 없음 | 최초 관리자 비밀번호. 기본 비밀번호는 없으며 직접 설정해야 합니다. |
| `DEVICE_ID` | `DEVICE-D1-001` | 기본 장치 ID |
| `DEVICE_TOKEN` | 없음 | 기본 장치 인증 토큰 |
| `NODE_ENV` | 없음 | `production`이면 세션 쿠키에 `Secure` 적용. HTTPS 필요 |

장치 인증은 기존과 같이 SHA-256 해시(`device.token_hash`)로 검사합니다. 서버와 펌웨어에 설정된 장치 ID·토큰이 일치해야 연결됩니다. 신규 장치는 장치 관리 화면에서 등록하고 발급된 토큰을 펌웨어에 설정합니다. 새로 발급하는 토큰은 재확인을 위해 AES-256-GCM 암호문(`device.token_ciphertext`)도 별도로 보관합니다. 서버 시작 시 기존 DB에는 암호문 열만 추가하며, 기존 인증 해시는 변경하지 않습니다.

### 장치 교체와 토큰 재사용

디바이스 관리 권한(기본 16레벨)으로 등록 장치의 편집 화면에서 토큰 확인·복사를 이용합니다. 확인 시에만 보호 API로 토큰을 가져오고 편집을 닫으면 제거합니다. 일반 장치·채널 목록에는 토큰을 포함하지 않습니다.

기존에 해시만 저장된 장치는 원문을 복원할 수 없습니다. 펌웨어 설정 등에 남아 있는 원래 토큰을 `기존 토큰 보관`으로 등록하면, 현재 해시와 일치하는 경우에만 암호화 보관합니다. 이 기능은 토큰을 새로 발급하거나 변경하지 않습니다. 기본 장치의 `.env` 토큰이 현재 해시와 일치하면 해당 값도 확인할 수 있습니다. 원래 토큰을 잃어버린 장치는 이 기능으로 같은 토큰을 복구할 수 없습니다.

토큰 보관 키는 최초 보관 시 서버 프로젝트의 `.factory-secrets/device-token.key`에 자동 생성됩니다. 이 경로는 Git에서 제외되며, DB 백업과 별도로 접근 권한을 제한해 안전하게 백업해야 합니다. 서버 이전 시 DB와 키 파일을 함께 복구하세요. **키 파일을 잃으면 암호화된 토큰을 복원할 수 없습니다.** Windows에서는 해당 폴더의 ACL도 서버 실행 계정과 신뢰하는 관리자만 접근하도록 제한하세요. 관리자 토큰 조회에는 HTTPS를 사용하세요.

고장 장치 교체 시 기존 장치를 네트워크에서 분리하고, 교체 장치 펌웨어에 동일한 장치 ID와 확인한 토큰을 설정합니다. 같은 인증값을 사용하는 두 장치를 동시에 연결하지 마세요.

## 디바이스 펌웨어와 안전

펌웨어 파일은 [device/Device.ino](device/Device.ino)와 [device/Device.h](device/Device.h)입니다. PlatformIO 설정은 [platformio.ini](platformio.ini)의 `device_d1_r1` 환경이며 현재 보드 설정은 ESP8266 Wemos D1입니다.

```bash
pio run -e device_d1_r1
pio device list
pio run -e device_d1_r1 -t upload --upload-port COM6
pio device monitor --port COM6 --baud 115200
```

`COM6`은 예시이므로 실제 포트로 바꾸세요. Wi-Fi, 서버 주소, TLS 사용 여부, 디바이스 ID·토큰은 `Device.ino`의 설정 구역에서 대상 환경에 맞춥니다. 펌웨어에 비밀값을 넣을 때는 공개 저장소에 올리지 말고, 이미 노출된 값은 교체하세요.

각 장치는 `IS1`~`IS16`, `OS1`~`OS16`의 논리 채널을 사용합니다. `IStr`는 장치에서 서버로 보내는 문자열이고 `OStr`는 서버에서 장치로 전달하는 문자열입니다. 논리 16채널 전체가 실제 GPIO에 연결된 것은 아닙니다. 현재 스케치는 시험용 입력 IS1과 물리 출력 OS1을 사용하며 다른 채널의 물리 입출력은 별도 배선·GPIO 매핑이 필요합니다.

장치 연결은 `/ws/device?deviceId=...` WebSocket 경로를 사용하고, 토큰은 `Authorization: Bearer` 헤더로 전달합니다. TLS 사용 시 서버 인증서와 장치 TLS 구성을 확인합니다. 실제 설비에 연결하기 전에 부하를 분리하고 핀 번호, 출력 극성, 재부팅 동작을 충분히 시험하세요. 논리 출력 상태는 별도 피드백 센서가 없다면 실제 설비 동작을 증명하지 않습니다.

## 데이터 구조

[schema.sql](schema.sql)과 서버 초기화 코드는 다음 테이블을 사용합니다.

| 테이블 | 역할 |
| --- | --- |
| `user_profile` | 회원, `login_id` 계정명, 계정 상태, 권한, 비밀번호 해시. 앱/API 응답은 기존처럼 `username` 필드 사용 |
| `user_setting` | 회원별 화면·알림 설정과 사용자 디자인 채널 선택·순서 |
| `company_organization` | 5개 3자리 조직 코드와 자동 입력용 표시 이름·활성 여부 |
| `user_register_comment` | 가입 신청·재신청·등급/조직 변경 요청·탈퇴 신청·승인·반려·정지의 코멘트와 작성자·처리 시각 누적 이력 |
| `site_permission_policy` | 사이트별 최초 기본값(`default_leble`), 현재 최소 레벨(`permisson_lebel`), 수정자·수정 시각 |
| `product` | 제품 코드, 누적·작업·목표 수량, 상태, 사용 여부(`is_enabled`)와 변경 정보 |
| `product_quantity_history` | 변경 시점의 누적·작업·목표 수량 스냅샷, 이전·신규 제품 상태, 사유·사용자·유형·시각. 제품 트리거가 기록 |
| `device` | 장치 등록·인증·접속 정보. 내부 숫자 PK는 `device_id`, 장치 식별 코드는 `device_code`, 표시 여부는 `is_visible`, 통신 사용 여부는 `is_enabled`입니다. API는 장치 식별 코드를 `device_id`로 반환합니다 |
| `device_channel` | 장치별 채널 상태·문자열·표시 및 제어 설정. 앱/API 표시 필드는 `is_visible` |
| `product_channel_mapping` | 제품과 출력 채널 연결 |
| `device_schedule` | 채널 예약과 실행 상태 |
| `device_command` | 출력 명령 큐와 ACK 상태. 예약 명령 여부는 `schedule_id` 유무로 판단 |
| `device_state_history` | 출력 상태 변경 이력과 `schedule_id` 기반 예약 출처 |

회원 삭제 시 개인 설정은 함께 삭제되고, 장치 삭제 시 해당 장치의 채널·명령·이력과 제품-채널 연결도 외래키에 의해 삭제됩니다. 제품 삭제 시 연결과 제품 수량 이력도 함께 삭제됩니다.

Device 표시 여부는 `device.is_visible`, 채널 표시 여부는 `device_channel.is_active`에 저장합니다. 기존 Device 테이블에 `is_active`가 있으면 서버 시작 시 값을 보존하며 `is_visible`로 컬럼명을 변경합니다. Device API와 관리 요청은 `is_visible`/`visible`을 사용합니다. Device의 `is_enabled`는 소켓 통신 여부이고, `device_schedule.is_enabled`는 개별 예약 실행 여부입니다. 예약 출처는 명령·상태 이력의 `schedule_id`로 식별합니다. 서버 시작 시 제한된 호환 마이그레이션으로 기존 스키마를 보정합니다.

## 문제 해결

| 증상 | 확인 사항 |
| --- | --- |
| 서버가 시작되지 않음 | DB 서비스 상태, DB 존재 여부, 접속정보·권한, 콘솔의 스키마 오류 확인 |
| 로그인 후 업무 화면 접근 거부 | 회원 승인·정지 상태와 해당 기능의 최소 등급 확인 |
| 제품 수량이 실시간 갱신되지 않음 | 브라우저 연결 상태와 실제 상태 변경 이벤트 확인. Invisible 제품은 생산 화면에서 숨겨지지만 DB 수량은 증가할 수 있음 |
| 채널 ON 후 수량이 증가하지 않음 | 제품-채널 연결과 실제 상태 변경 이벤트 확인. Invisible 디바이스·채널 상태는 증가를 막지 않음 |
| 디바이스가 연결되지 않음 | ID·토큰 일치, Wi-Fi, 서버 주소·포트, WS/WSS 설정 확인. Invisible 상태는 장치 인증을 막지 않음 |
| 명령 후 출력 상태가 변하지 않음 | 명령 큐 상태와 디바이스 ACK·실제 상태 보고를 구분해 확인 |
| 화면 상태와 실제 설비가 다름 | 상태가 논리값인지 확인하고 배선·출력 극성·피드백 센서를 점검 |

오류 문의 시 발생 시각, 화면 경로, 디바이스 ID, 채널, 오류 메시지를 기록하세요. 비밀번호·토큰·DB 접속정보는 로그나 문의 내용에 포함하지 마세요.

## 개발과 검증

```bash
npm test
node --check server.js
node --check public/product-channel-link.js
```

`npm test`는 저장소의 Node.js 테스트를 실행합니다. 테스트 결과는 실제 MySQL/MariaDB 마이그레이션, 브라우저 간 실시간 동작, 물리 디바이스·설비 시험을 대신하지 않습니다. 펌웨어 빌드는 PlatformIO 명령을 사용합니다.

- 서버 진입점과 API·WebSocket·DB 초기화: [server.js](server.js)
- DB 신규 설치 스키마: [schema.sql](schema.sql)
- 사용자 화면 권한·공통 화면 상태: [public/page-settings.js](public/page-settings.js)
- 생산 현황과 입력 화면: [public/product-view.js](public/product-view.js), [public/product-control.js](public/product-control.js)
- 제품-채널 매핑 화면: [public/product-channel-link.html](public/product-channel-link.html), [public/product-channel-link.js](public/product-channel-link.js)
- 디바이스 화면과 동적 채널 UI: [public/device-view.js](public/device-view.js), [public/device-control.js](public/device-control.js), [public/device-active.js](public/device-active.js)
- 테스트: [test/device-protocol.test.js](test/device-protocol.test.js)
