# KIMS SMART FACTORY V1.0

공장의 생산수량·작업 상태와 장치의 입력·출력 상태를 웹에서 확인하고 관리하는 프로그램입니다. 사용자는 권한에 따라 생산 정보를 조회하거나 입력하고, 관리자는 회원·제품·장치를 등록하고 운영합니다.

이 문서는 **사용자 이용 → 등급별 권한 → 관리자 운영 → 설치 → 문제 해결·운영 주의 → 기술 참고** 순서로 구성되어 있습니다. 이미 운영 중인 사이트를 이용한다면 사용자 안내와 권한 표부터 확인하고, 처음 설치한다면 설치와 실행을 마친 뒤 관리자 운영을 진행하세요.

> 안전 안내: 현재 장치 펌웨어는 8개 논리 채널과 일부 보드 시험 기능을 제공합니다. 완성된 8채널 물리 제어기는 아닙니다. 실제 설비에 연결하기 전에 핀 매핑·출력 극성·재부팅 동작을 확인하고 부하를 분리해 시험해야 합니다.

## 사용자 안내

### 처음 이용하는 순서

1. 관리자가 안내한 사이트 주소에 접속합니다. 기본 화면은 생산 현황이며, 로그인하지 않았다면 로그인 화면으로 이동합니다.
2. 계정이 없다면 회원가입 화면에서 가입을 신청합니다. 새 계정은 **1등급·승인 대기**로 만들어집니다.
  필수 입력은 아이디·비밀번호·비밀번호 확인뿐이며, 이름·지역·회사·직위·전화번호·이메일은 선택입니다. 선택 항목을 입력하면 길이와 형식을 검사합니다.
3. 관리자의 승인을 기다립니다. 승인 대기 중에는 회원정보 확인·수정을 위해 로그인할 수 있지만 업무 화면은 사용할 수 없습니다.
4. 승인 후 다시 로그인하고, 상단에 표시된 이름·아이디·등급을 확인합니다.
5. 필요한 메뉴를 선택합니다. 메뉴가 보이지 않거나 접근이 거부되면 회원 상태와 등급을 관리자에게 확인합니다.
6. 공용 PC에서 작업을 마치면 로그아웃합니다.

| 이용 목적 | 화면 |
| --- | --- |
| 로그인 | [회원 로그인](public/user-login.html) |
| 계정 만들기 | [회원가입 신청](public/user-register.html) |
| 본인 정보·비밀번호·탈퇴 신청 | [회원정보](public/user-profile.html) |
| 알림음·테마·표시 항목 설정 | [개인 설정](public/user-setting.html) |

위 링크는 저장소의 화면 파일입니다. 실제 이용할 때는 실행 중인 사이트의 메뉴를 사용합니다. 예를 들어 생산 현황의 접속 경로는 `/`, 회원정보는 `/user-profile.html`입니다.

### 기능별 권한

등급 숫자가 높을수록 아래 등급의 업무 기능을 포함합니다. 메뉴 표시는 편의 기능이며, 서버는 로그인과 계정 상태를 확인하고 등급 제한이 설정된 화면·API에 해당 최소 등급을 적용합니다.

| 등급 | 권한 |
| --- | --- |
| 1 | 생산 현황과 장치 상태 조회. 회원정보와 개인 설정 사용 |
| 2 | 1등급 권한 + 생산수량·작업 상태 입력 |
| 3 | 2등급과 동일. 별도 기능 추가 없음 |
| 4 | 2등급 권한 + 장치 ON/OFF 제어, 전체 예약 조회·등록·수정·중지·삭제 |
| 5 | 4등급과 동일. 별도 기능 추가 없음 |
| 6 | 4등급 권한 + 제품 등록·수정·삭제 |
| 7 | 6등급과 동일. 별도 기능 추가 없음 |
| 8 | 6등급 권한 + 회원 승인·관리, 장치·채널 관리 |
| 9 | 8등급 권한. 1~8등급 회원 관리 가능 |
| 10 | 모든 업무 권한. 1~9등급 회원 관리 가능. 최초 관리자 등급 |

회원 등급은 본인 계정에서 변경할 수 없습니다. 관리자는 자신보다 낮은 등급의 다른 회원을 수정할 수 있으며, 새 등급은 관리자 자신의 등급과 같게 설정할 수도 있습니다. 예를 들어 8등급 관리자는 1~7등급 회원을 8등급까지 올릴 수 있습니다. 같은 등급이 된 뒤에는 서로의 계정을 관리할 수 없으며, 동급·상위 회원도 수정할 수 없습니다. 자기 계정의 등급을 높이는 것도 허용되지 않습니다.

회원가입 계정은 `PENDING` 상태의 1등급으로 생성됩니다. 승인되면 1등급 `APPROVED`로 시작하며, 8등급 이상은 관리자 승인이 되지 않은 계정에도 업무 접근 예외가 있습니다. 단, 정지된 계정은 등급과 관계없이 업무 기능을 사용할 수 없습니다. 회원정보는 로그인한 본인, 개인 설정은 로그인한 활성 계정이 이용합니다.

| 기능 | 최소 등급 | 화면 |
| --- | --- | --- |
| 생산 현황·장치 상태 조회 | 1 | [생산 현황](public/product-view.html), [장치 보기](public/device-view.html) |
| 생산수량·작업 상태 입력 | 2 | [생산 입력](public/product-control.html) |
| 장치 출력 제어·전체 예약 관리 | 4 | [장치 제어](public/device-control.html), [예약 관리](public/device_schedule.html) |
| 제품 등록·수정·삭제 | 6 | [제품 관리](public/product-admin.html) |
| 회원 승인·권한·상태 관리 | 8 | [회원 관리](public/user-admin.html) |
| 장치·채널 관리 | 8 | [장치 관리](public/device-admin.html) |

### 회원 상태에 따른 이용 범위

| 상태 | 사용자에게 의미하는 내용 | 다음 행동 |
| --- | --- | --- |
| `PENDING` | 가입 승인 대기 | 정보를 확인하고 관리자 승인 대기 |
| `APPROVED` | 승인 완료 | 등급에 맞는 업무 기능 이용 |
| `REJECTED` | 가입 신청 반려 | 회원정보 수정 후 재신청 |
| `SUSPENDED` | 계정 정지 | 회원정보 화면에서 정보 확인 후 관리자 문의 |
| `WITHDRAWAL_PENDING` | 탈퇴 처리 대기 | 관리자 승인 전에는 신청 취소 가능 |

승인 대기·반려·정지·탈퇴 대기 계정은 로그인 후 회원정보 화면으로 안내됩니다. **탈퇴 신청은 즉시 삭제가 아니지만, 관리자가 승인하면 계정이 실제 삭제됩니다.**

### 생산 현황 조회와 입력

생산 현황에는 제품별 수량, 목표수량, 달성률, 작업 상태, 변경자와 변경 시각이 표시됩니다. 변경자는 마지막으로 제품을 수정한 로그인 아이디입니다. 개인 설정에서 숨긴 항목은 보이지 않을 수 있습니다.

1. 조회만 필요하면 생산 현황 화면을 엽니다.
2. 수량이나 상태를 변경하려면 2등급 이상 계정으로 생산 입력 화면을 엽니다.
3. 대상 제품을 확인하고 수량 또는 상태를 변경합니다.
4. 저장 결과를 확인합니다. 서버는 변경 회원과 시각을 기록하고 연결된 화면에 변경 내용을 전달합니다.

작업 상태는 **대기·생산중·수리중·완료·정지**를 사용합니다. 저장 실패나 연결 끊김이 보이면 반영됐다고 가정하지 말고, 재연결 후 최신 값을 확인하세요.

### 장치 조회와 출력 제어

장치 보기·제어 화면에는 **활성 장치와 활성 채널**이 표시됩니다. 여러 장치가 있다면 장치 ID와 이름을 먼저 확인합니다.

| 표시 항목 | 의미 |
| --- | --- |
| `IS1`~`IS8` | 장치의 채널별 입력 상태 |
| `OS1`~`OS8` | 장치가 보고한 채널별 출력 상태 |
| `IStr1`~`IStr8` | 장치에서 서버로 보내는 입력 문자열 |
| `OStr1`~`OStr8` | 서버에서 장치로 보내는 출력 문자열 |
| 최근 변경 출처·시각 | 실제 출력이 마지막으로 바뀐 출처와 시각 |

조회 화면은 상태를 보여줄 뿐 출력 명령을 보내지 않습니다. 제어하려면 4등급 이상 계정으로 장치 제어 화면을 사용합니다.

1. 장치 ID·채널·현재 출력 상태를 확인합니다.
2. 필요한 경우 해당 ON/OFF 요청의 출력 문자열을 입력합니다.
3. ON 또는 OFF를 누릅니다.
4. 장치가 처리한 실제 출력 상태가 화면에 반영되는지 확인합니다.

> 버튼을 누르거나 서버가 명령을 저장했다는 사실만으로 출력이 바뀐 것은 아닙니다. 장치의 처리 응답과 실제 상태 보고를 확인해야 합니다. 오프라인 장치의 명령은 대기할 수 있으므로, 재연결 시 실행 가능성을 고려해 안전하게 제어하세요.

웹 명령은 입력 IS를 바꾸지 않으므로 IS와 OS가 다를 수 있습니다. 이후 장치 입력이 바뀌면 입력에 맞춰 출력이 다시 바뀔 수 있습니다. ON/OFF별 OStr 입력란이 비어 있으면 빈 문자열이 전송되어 화면에 표시되는 기존 OStr 값을 지웁니다.

화면의 OS는 장치가 보고한 논리 출력 상태입니다. 별도 피드백 센서가 없다면 릴레이 접점이나 실제 설비가 의도대로 동작했는지까지 증명하지는 않습니다.

### 채널 예약

4등급 이상은 장치 제어 화면의 채널 버튼에서 예약을 등록할 수 있으며, [예약 관리](public/device_schedule.html) 화면에서 전체 예약을 조회·등록·수정·중지·삭제할 수 있습니다. 실행 시각에 날짜와 시·분을 입력합니다. 별도의 실행 시·분 입력은 사용하지 않습니다.

서버는 5초 간격으로 실행 시각이 된 활성 예약을 확인합니다. 예약 실행이 명령 큐에 등록된 상태와 장치가 실제 상태를 보고한 상태는 다르므로, 실행 결과와 장치 응답을 확인하세요.

예약의 전송 문자열은 `OStr`입니다. 예약 실행 시 장치의 출력 문자열로 전달하며 입력 문자열 `IStr`는 변경하지 않습니다. 채널 예약 버튼에는 가장 가까운 활성 예약의 시각·ON/OFF와 해당 예약에 저장된 `OStr`가 표시됩니다. 예약 문자열을 비우면 실행 시 채널의 기존 출력 문자열을 유지합니다.

| 반복 유형 | 실행 시각에서 사용하는 기준 |
| --- | --- |
| 1회 | 입력한 날짜와 시·분에 한 번 실행 |
| 매시간 | 입력한 분에 매시간 실행 |
| 매일 | 입력한 시·분에 매일 실행 |
| 반복 요일 | 선택한 요일마다 입력한 시·분에 실행 |
| 매월 | 입력한 일자와 시·분에 실행. 말일을 선택하면 매월 마지막 날 실행 |
| 매년 | 입력한 월·일과 시·분에 실행 |

반복 유형은 하나만 선택할 수 있으며, 반복 요일 안에서는 여러 요일을 선택할 수 있습니다. 시각은 한국 표준시(KST) 기준입니다. 해당 일자가 없는 달은 건너뛰며, 매년 2월 29일 예약은 윤년에 실행합니다. 1회 예약은 현재 이후의 시각이어야 합니다.

### 개인 설정

개인 설정에서 알림음 종류·크기·사용 여부, 밝은/어두운 테마, 일반/간결/크게 보기, 생산현황 열과 요약, 날짜 형식, 장치 문자열·입력란 표시를 선택할 수 있습니다.

설정은 회원별로 DB에 저장되므로 다른 브라우저에서도 복원됩니다. 테마·보기 모드는 빠른 초기 표시를 위해 브라우저에 캐시하며, 장치 화면에 다시 돌아오면 문자열 표시 설정을 서버에서 다시 읽습니다. **표시를 숨겨도 데이터 통신과 출력 제어 동작은 바뀌지 않습니다.**

## 연결 상태 읽기

사용자 정보 뒤의 문구는 **현재 페이지가 어떤 방식으로 서버와 연결되는지**에 따라 의미가 달라집니다. 문구에 마우스를 올리면 확인 대상을 볼 수 있습니다.

| 표시 위치·화면 | 확인 대상 | 확인 방식 |
| --- | --- | --- |
| 생산 조회·입력, 장치 조회·제어의 상단 | 브라우저와 서버 사이의 WebSocket | 기존 소켓의 연결·종료·오류 이벤트 반영 |
| 제품·장치·회원 관리, 회원정보·개인 설정의 상단 | 브라우저가 HTTP 서버 응답을 받을 수 있는지 | 최초 진입 및 확인 완료 후 30초 간격, 응답 제한 5초 |
| 장치 카드의 연결됨/연결 안 됨 | 서버와 해당 장치 사이의 연결 | 장치 연결 상태 이벤트 반영 |

로그인·회원가입 화면에는 상단 연결 상태를 표시하지 않습니다. 비소켓 화면은 `/api/server-status`로 확인하며 DB 조회나 별도 WebSocket 연결을 만들지 않습니다. 화면 복귀·네트워크 복구 시에도 HTTP 상태를 다시 확인합니다.

| 문구 | 소켓 화면 | HTTP 확인 화면 |
| --- | --- | --- |
| `CONNECTING` | 소켓 연결 또는 재연결 중 | 서버 응답 확인 중 |
| `ONLINE` | 소켓이 연결됨 | 서버가 정상 응답함 |
| `OFFLINE` | 소켓 오류 또는 연결 종료 | 요청 실패, 오류 응답 또는 시간 초과 |

**상단 ONLINE은 장치 정상 작동이나 DB 정상 연결을 보장하지 않습니다.** 장치가 연결되지 않아도 브라우저와 서버는 연결될 수 있고, 서버가 응답해도 DB 작업은 실패할 수 있습니다. 각 장치의 연결 표시, 저장 결과, 실제 출력 상태를 함께 확인합니다.

연결 상태 표시는 항상 즉시 끊김을 감지하는 것은 아닙니다. 소켓은 연결 유지 확인이 실패한 뒤 종료될 수 있고, HTTP 화면은 다음 확인 시점까지 이전 상태가 남을 수 있습니다. 서버가 응답하지 않을 때는 마지막으로 표시된 사용자 정보가 유지될 수 있습니다.

## 관리자 운영

### 최초 운영 준비 순서

1. [설치와 실행](#설치와-실행)에 따라 DB와 서버를 준비하고 최초 10등급 관리자 계정으로 로그인합니다.
2. 제품 관리에서 제품을 등록합니다.
3. 장치를 사용할 경우 장치 관리에서 등록·활성 상태·채널 이름을 확인하고, 펌웨어의 ID·토큰을 맞춥니다.
4. 설비 부하를 분리한 상태에서 [장치 설정과 시험](#장치-설정과-시험)을 진행합니다.
5. 사용자 가입 신청을 확인하고 승인합니다. 조회 사용자는 1등급, 입력·제어 담당자는 필요한 최소 등급으로 설정합니다.
6. 사용자별로 로그인·조회·입력·제어 가능 범위를 확인한 뒤 운영을 시작합니다.

### 회원 승인과 권한 관리

회원 관리는 8등급 이상이 사용할 수 있습니다. 가입 신청 정보를 확인해 승인 또는 반려하고, 승인 후 실제 업무에 필요한 등급을 부여합니다. 신규 가입 승인은 1등급부터 시작합니다.

관리자는 **자신보다 낮은 등급의 회원만** 관리하며, 부여할 등급도 자신의 등급보다 낮아야 합니다. 자기 자신의 등급 변경과 자기 삭제는 할 수 없습니다. 동급·상위 관리자의 계정을 수정할 수 있다고 가정하지 마세요.

회원 수정, 정지·상태 변경, 탈퇴 처리, 삭제, 관리자 메모를 관리합니다. 관리자 메모는 본인 회원정보 API에 포함되지 않습니다. 정지·삭제 시 해당 회원의 실시간 연결도 종료됩니다. 정지 계정은 회원정보 접근을 위해 세션을 유지할 수 있지만 삭제 계정의 세션은 제거됩니다.

### 제품과 장치 관리

| 관리 대상 | 운영 절차 | 주의사항 |
| --- | --- | --- |
| 제품 | 제품코드·제품명·수량·목표수량·상태 등록 → 작업자 입력 → 생산 현황 확인 | 삭제하면 제품 DB 행이 실제 삭제됨 |
| 장치 | 장치 등록 → 토큰 보관 → 장치 활성·채널 이름·활성 여부·순서 설정 → 연결 시험 | 장치 삭제 시 채널·명령·이력도 삭제됨 |
| 예약 | 4등급 이상은 전체 예약 조회·등록·수정·중지·삭제 | 명령 큐 등록과 장치 ACK를 구분해 실행 결과 확인 |
| 장치 토큰 | 등록 시 받은 원본 토큰을 안전하게 전달하고 펌웨어에 설정 | 서버는 해시를 저장하므로 원본 토큰을 안전하게 보관해야 함 |

환경변수의 기본 장치 토큰을 바꿔도 기존 등록 장치의 토큰이 자동 교체되지는 않습니다. 토큰을 교체할 때는 서버의 등록 정보와 장치 펌웨어를 함께 맞추고 재연결을 확인합니다.

### 일상 점검과 재시작

업무 시작 시 DB·서버 로그, 화면 연결 상태, 각 장치의 연결과 실제 출력 상태를 확인합니다. 대기 중인 출력 명령이 있다면 재연결 전에 내용을 점검합니다.

서버 종료는 로컬 터미널에서 `Ctrl+C`, 배포 환경에서는 해당 서비스의 중지 기능을 사용합니다. 다시 시작할 때는 설치와 실행의 `npm start`를 사용합니다. **세션은 서버 메모리에 있으므로 재시작 후 사용자는 다시 로그인해야 합니다.** 현재 구조의 DB·제품·채널 설정은 정상 재시작만으로 초기화되지 않습니다.

환경변수를 변경하면 서버 재시작 또는 재배포가 필요합니다. 장치 펌웨어를 변경하면 빌드·재업로드가 필요하며, 웹 스크립트 변경 후에는 페이지를 새로고침합니다. DB 구조 변경은 재시작과 별개이므로 [수동 이름 마이그레이션](#수동-이름-마이그레이션) 절차를 따릅니다.

### 백업과 삭제 전 확인

제품·회원·장치 삭제와 탈퇴 승인 전에는 대상과 삭제 범위를 확인합니다. DB 변경이나 버전 이전 전에는 전체 백업을 만들고 복원 가능 여부를 시험합니다. 특히 장치 삭제는 관련 채널·명령·출력 이력을 함께 삭제합니다.

SQL 백업에는 회원정보·비밀번호 해시·장치 토큰 해시가 포함될 수 있으므로 접근을 제한합니다. 실제 비밀번호, 장치 토큰, DB 접속정보를 공개 저장소나 로그에 남기지 않습니다.

## 설치와 실행

### 1. 준비

- Node.js와 npm을 설치합니다. 테스트에는 `node --test`를 지원하는 Node.js가 필요합니다.
- MySQL 또는 MariaDB와 새 데이터베이스를 준비합니다. 구형 DB를 자동 이전하는 코드는 사용하지 않습니다.
- 펌웨어를 빌드할 때는 PlatformIO와 USB 드라이버, 해당 ESP8266 보드를 준비합니다.

### 2. 패키지 설치

프로젝트 루트에서 실행합니다.

```bash
npm install
```

### 3. DB 준비

환경에 맞는 방법을 하나 선택합니다. 기존 운영 DB에 신규 설치용 SQL을 실행하지 않습니다.

| 현재 환경 | 준비 방법 |
| --- | --- |
| `factory` DB가 없고 DB 생성 권한이 있음 | [schema.sql](schema.sql) 실행. DB·8개 테이블·예시 제품·장치를 생성 |
| 관리 콘솔에서 빈 DB를 제공받음 | 해당 이름을 `DB_NAME`에 지정. 서버가 8개 테이블을 생성하며 예시 제품은 제품 관리 화면에서 직접 등록 |
| 현재 이름·컬럼 구조의 DB가 이미 있음 | 기존 DB와 `DB_NAME`을 그대로 사용. 초기 SQL과 마이그레이션을 재실행하지 않음 |
| 이름 변경 직전의 7개 테이블 구조를 사용 중 | 백업 후 [수동 이름 마이그레이션](#수동-이름-마이그레이션) 적용 |
| 그보다 오래되었거나 다른 구조의 DB | 기존 DB를 보존하고 별도 새 DB 준비. 자동 이전은 지원하지 않음 |

[schema.sql](schema.sql)은 `CREATE DATABASE factory`와 `USE factory`를 사용합니다. 다른 이름으로 신규 설치한다면 두 구문과 `DB_NAME`을 함께 맞춥니다. 서버는 DB 자체를 생성하거나 기존 테이블 이름을 자동 변경하지 않습니다.

선택 회원정보 정책을 적용하기 전의 기존 DB는 서버를 중지하고 백업한 뒤, SQL 클라이언트에서 실제 `DB_NAME`의 DB를 선택하여 [migrate-optional-user-profile.sql](migrate-optional-user-profile.sql)을 실행합니다. 이름의 기본값과 이메일의 `NULL` 허용을 변경하고 빈 이메일을 `NULL`로 정리하며, 기존 이메일의 고유 제약은 유지합니다. 적용 후 서버를 다시 시작합니다. 신규 DB는 [schema.sql](schema.sql)에 이미 반영되어 있어 이 SQL이 필요하지 않습니다.

### 4. 환경 설정

프로젝트 루트의 `.env`에 DB 접속정보와 최초 관리자 정보를 입력합니다. 실제 비밀번호와 토큰은 공개 저장소에 올리지 않습니다. 형식은 [환경변수](#환경변수)를 참고하세요.

### 5. 실행과 첫 로그인

```bash
npm start
```

기본 접속 주소는 `http://localhost:8080`입니다. `PORT`를 변경했다면 해당 포트로 접속합니다.

서버는 DB 이름 검사 → 테이블 준비 → 최초 관리자 준비 → HTTP 요청 수신 순서로 시작합니다. 지원하지 않는 이전 테이블 이름이나 필수 컬럼이 없는 DB는 안내와 함께 중단합니다. 시작 시 누락된 호환 컬럼을 추가하거나 예약 문자열 컬럼을 `istr_payload`에서 `ostr_payload`로 바꾸는 제한된 호환 처리는 수행할 수 있으며, 필수 테이블 생성에 실패하면 시작하지 않습니다.

`MASTER_USERNAME`과 `MASTER_PASSWORD`를 설정하면 최초 10등급 관리자를 생성하거나 동일 계정을 관리자 상태로 확인합니다. 일반 사용자는 가입 신청 후 승인을 받아 이용합니다. 재시작 시 기존 비밀번호·장치 토큰·채널 설정·생산 데이터를 초기화하지 않습니다.

## 환경변수

### DB와 서버

```dotenv
DB_CLIENT=mysql
DB_HOST=localhost
DB_PORT=3306
DB_USER=factory_user
DB_PASSWORD=replace_with_database_password
DB_NAME=factory
DB_POOL_SIZE=5
PORT=8080
```

| 항목 | 의미 |
| --- | --- |
| `DB_CLIENT` | `mysql` 또는 `mariadb`. 기본값은 `mysql` |
| `DB_HOST`, `DB_PORT` | 실제 DB 호스트와 포트 |
| `DB_USER`, `DB_PASSWORD` | DB 조회·갱신 및 테이블 생성 권한을 가진 계정 |
| `DB_NAME` | 실제로 존재하는 데이터베이스 이름 |
| `DB_POOL_SIZE` | DB 연결 풀 크기. 기본값은 `5` |
| `PORT` | 서버 포트. 기본값은 `8080` |
| `NODE_ENV` | `production`이면 세션 쿠키에 `Secure`를 설정하므로 HTTPS가 필요 |

Cloudtype에서는 서비스 이름이 아니라 실제 DB 이름을 `DB_NAME`에 지정합니다. 환경변수 변경 후에는 재배포 또는 서버 재시작이 필요합니다.

### 최초 관리자

```dotenv
MASTER_USERNAME=master
MASTER_PASSWORD=replace_with_strong_password
MASTER_NAME=관리자
MASTER_REGION=대한민국
MASTER_COMPANY=회사명
MASTER_POSITION=관리자
MASTER_PHONE=010-0000-0000
MASTER_EMAIL=admin@example.com
```

최초 관리자는 `MASTER`, 10등급, `APPROVED` 상태로 준비됩니다. 일반 가입 계정의 비밀번호는 `crypto.scrypt` 해시로 저장합니다.

### 기본 Device

```dotenv
DEVICE_ID=DEVICE-D1-001
DEVICE_TOKEN=replace_with_random_device_token
```

기본 장치 ID와 토큰은 펌웨어의 `DEVICE_ID`, `DEVICE_TOKEN`과 일치해야 합니다. 다른 장치는 장치 관리 화면에서 등록하고 발급된 토큰을 사용합니다. 서버는 장치 토큰을 SHA-256 해시로 보관하며 원본 토큰 없이 연결을 허용하지 않습니다.

`DEVICE_ID`가 없으면 이전 설정 키 `DIVICE_ID`, `DEVICE_DEVICE_ID`, `WEMOS_DEVICE_ID` 순서로 장치 ID를 읽습니다. `DEVICE_TOKEN`이 없으면 `DEVICE_DEVICE_TOKEN`, `WEMOS_DEVICE_TOKEN` 순서로 토큰을 읽습니다. 새 키와 이전 키가 함께 있으면 새 키가 우선합니다.

이미 등록된 장치의 토큰 해시는 초기화 시 덮어쓰지 않습니다. 환경변수만 바꿔도 기존 장치의 토큰이 자동 교체되는 것은 아닙니다. 이전 환경변수 이름은 호환 처리에서만 지원합니다.

## 장치 설정과 시험

### 연결 설정

[device/Wemos-D1-001.ino](device/Wemos-D1-001.ino)에서 다음 항목을 실제 환경에 맞춥니다. 공통 통신·채널 처리는 [device/WemosDevice.h](device/WemosDevice.h)에 있습니다.

| 설정 | 설명 |
| --- | --- |
| `WIFI_SSID`, `WIFI_PASSWORD` | Wi-Fi 정보. 빈 비밀번호는 개방형 네트워크 |
| `SERVER_HOST` | 프로토콜·경로를 제외한 서버 호스트 또는 IP |
| `SERVER_PORT` | 로컬 WS는 보통 `8080`, HTTPS/WSS 배포는 보통 `443` |
| `SERVER_USE_TLS` | 로컬 WS는 `false`, WSS는 `true` |
| `DEVICE_ID`, `DEVICE_TOKEN` | 서버에 등록한 ID와 토큰 |

장치는 `/ws/device?deviceId=...`로 접속하며 토큰은 `Authorization: Bearer` 헤더로 전송합니다. 서버는 등록 여부·활성 상태·토큰 해시를 검사한 뒤 메시지를 처리합니다. 토큰을 URL에 넣지 않습니다.

### 빌드·업로드

[platformio.ini](platformio.ini)의 소스 폴더는 `device`, 환경은 `device_d1_r1`, 보드는 `d1`, 시리얼 속도는 `115200`입니다.

```bash
pio run -e device_d1_r1
pio device list
pio run -e device_d1_r1 -t upload --upload-port COM6
pio device monitor --port COM6 --baud 115200
```

`pio`를 PATH에서 찾지 못하면 PlatformIO 확장의 Build/Upload/Monitor 기능을 사용합니다. `COM6`은 예시이며 실제 포트로 바꿉니다.

### 현재 보드 시험 동작

8채널은 논리 변수로 관리하며, 현재 코드에는 다음 시험 기능이 포함되어 있습니다.

| 시리얼 입력 | 반영 값 |
| --- | --- |
| `0` | `IS1=false`, `IStr1="Ch1 off"` |
| `1` | `IS1=true`, `IStr1="Ch1 on"` |
| `2` | `IStr1="alarm"`. 입력·출력 상태는 직접 변경하지 않음 |

`OS1`은 D9의 HIGH/LOW 출력에 반영됩니다. D7 내부 풀업 입력은 LOW일 때 ON, HIGH일 때 OFF이며, 누름과 해제 모두 50ms 연속 유지된 입력만 IS1/OS1에 반영합니다. 스케치의 `pinStateChanged()`와 공통 헤더의 `updateButtonDebounce()`가 입력 안정화를 처리합니다. 시리얼 입력도 통신 처리 전에 반영합니다. 문자열만 바꾸는 `2` 입력은 자체적으로 상태 보고를 예약하지 않습니다.

통신 단절 중 상태 보고 예약을 유지하며, 재연결 시 마지막 IS/OS/문자열을 서버로 보고합니다. 전송 실패 시 재시도하지만 오프라인 변화의 전체 이력이나 전원 차단 전 상태를 저장하지는 않습니다. 버튼 입력은 폴링 방식이므로 네트워크 처리가 오래 블로킹되면 반영도 늦어질 수 있습니다. 하드웨어 필터와 독립 안전회로가 필요하며 MCU 정지 상황의 무지연 및 설비 안전까지 보장하지 않습니다. D9는 GPIO3/UART RX와 겹치므로 시리얼 연결과 실제 배선을 확인하세요.

나머지 채널의 물리 DI/DO 및 릴레이 매핑은 별도로 구현해야 합니다. 실제 부하는 분리한 상태에서 업로드·재부팅·출력 극성을 확인합니다. 현재 코드를 완성된 8채널 물리 제어기로 간주하지 않습니다.

## 문제 해결

먼저 사용자 화면에서 확인할 수 있는 항목을 점검하고, 해결되지 않으면 관리자에게 발생 시각·페이지·장치 ID·채널·오류 문구를 전달합니다. 비밀번호와 토큰은 전달 자료에 포함하지 않습니다.

| 증상 | 사용자 또는 관리자의 확인 순서 |
| --- | --- |
| 로그인 후 업무 화면을 사용할 수 없음 | 회원 상태 확인 → 승인 여부 확인 → 기능별 최소 등급 확인 |
| 상단에 `OFFLINE` 표시 | 인터넷·사이트 접속 확인 → 해당 페이지가 소켓 확인인지 HTTP 확인인지 구분 → 서버 로그 확인 |
| 상단은 `ONLINE`인데 장치는 연결 안 됨 | 장치 전원·Wi-Fi 확인 → 장치 활성 상태 확인 → ID·토큰·WS/WSS 호스트·포트 확인 |
| ON/OFF를 눌러도 출력 표시가 바뀌지 않음 | 장치·채널 선택 확인 → 장치 연결 확인 → 명령 대기·처리 결과와 실제 상태 보고 확인 |
| 화면에 장치나 채널이 보이지 않음 | 장치 등록·활성 상태와 채널 활성 여부 확인 |
| 입력 IS와 출력 OS가 다름 | 웹 제어 이력과 실제 상태 확인. 웹 명령은 IS를 바꾸지 않으므로 차이가 있을 수 있음 |
| 새로고침 후 다시 로그인해야 함 | 세션 만료·서버 재시작 여부 확인 |
| `Unknown database` | 실제 DB 이름과 `DB_NAME` 확인. 서버는 DB 자체를 만들지 않음 |
| 이전 DB 구조·컬럼 오류 | 백업 후 기존 구조와 마이그레이션 적용 상태 확인. 운영 DB를 임의로 삭제하지 않음 |
| DB 연결 실패 | 호스트·포트·계정·권한·방화벽 및 DB 서비스 접근 가능 여부 확인 |
| 이메일 중복 오류 | 기존 회원의 이메일과 UNIQUE 조건 확인 |
| 테스트에서 파일 없음 또는 HTML 비교 실패 | [검증과 유지보수](#검증과-유지보수)의 테스트 한계 확인 |

연결 복구 뒤에는 최신 데이터를 다시 확인합니다. 저장 실패나 대기 명령을 확인하지 않고 같은 제어를 반복하지 마세요. DB 복구·마이그레이션·장치 업로드는 관리자가 안전한 절차에 따라 수행합니다.

## 운영 주의사항

- 실제 비밀번호·장치 토큰을 `.env`, 소스 코드, 로그, 공개 저장소에 노출하지 않습니다. 이미 노출된 토큰은 교체합니다.
- 세션은 서버 메모리에 있어 서버 재시작 시 다시 로그인해야 합니다. 여러 서버 인스턴스의 세션 공유는 별도로 고려해야 합니다.
- WSS의 암호화와 서버 인증은 별개입니다. 현재 TLS 구성에 CA 또는 지문 검증이 없으므로 외부망에서는 인증서 검증 정책이 필요합니다.
- 장치 입력 변화와 웹 명령은 모두 출력을 바꿀 수 있습니다. 업로드·재부팅·연결 시험 전에 실제 부하를 분리하고 D9의 보드 핀 매핑과 출력 극성을 확인합니다.
- 회원 탈퇴 승인, 회원·제품·장치 삭제는 실제 데이터를 삭제합니다. 관련 데이터의 연쇄 삭제도 확인합니다.
- DB 연결 실패는 호스트·포트·계정·권한·DB 이름부터 확인합니다. `Unknown database`는 지정한 DB가 실제로 존재하는지 확인합니다.
- 구형 DB에 현재 테이블이 없거나 컬럼이 다르면 지원하는 이전 구조인지 확인하고 백업 후 수동 마이그레이션 또는 별도의 새 DB를 사용합니다. 기존 테이블을 임의로 삭제하지 않습니다.
- 기존 DB의 중복 이메일은 UNIQUE 인덱스 생성을 막을 수 있습니다. 오류 로그를 확인하고 중복을 정리합니다.
- 신규 SQL은 기존 운영 DB에 재실행하지 않습니다. 새 DB 이름과 환경설정을 확인한 뒤 서버를 시작하거나 재배포합니다.

### 8채널 통신 흐름

### 데이터 전송과 연결 유지 주기

| 상황 | 통신 시점 |
| --- | --- |
| 브라우저 최초 연결·재연결 | 제품 목록 전송. 장치 화면은 구독 후 초기 상태·이력·명령 수신 |
| 제품 수량·상태·정보 변경 | 변경이 발생하면 연결된 화면에 전송 |
| 장치 입력 변화·웹 제어 명령 | 입력 안정화 또는 명령 처리에 따라 상태·응답 전송 |
| 장치 최초 연결·재연결 | hello와 8채널 상태 보고 |
| 서버의 소켓 연결 유지 확인 | 현재 코드에서 15초마다 Ping 전송 |
| 장치의 소켓 연결 유지 확인 | 현재 `WS_PING_INTERVAL_MS=15000`, Pong 제한 3초 |
| 비소켓 화면의 HTTP 확인 | 확인 완료 후 30초마다 요청, 응답 제한 5초 |

**15초는 생산·채널 데이터를 보내는 주기가 아니라 연결 유지 확인 주기입니다.** 데이터는 사건이 발생할 때 전송됩니다. 입력은 50ms 안정화 후 반영하며, 시간이 지났다는 이유만으로 모든 채널 상태를 반복 전송하지 않습니다. 문자열만의 변화도 항상 상태 보고를 예약하는 것은 아닙니다.

연결 유지 확인은 [server.js](server.js)의 `websocketHeartbeat`와 [device/WemosDevice.h](device/WemosDevice.h)의 `WS_PING_INTERVAL_MS`에서 설정합니다. 주기를 늘리면 확인 통신은 줄지만 연결 끊김 발견이 늦어질 수 있습니다. HTTP 상태 확인 주기는 [public/page-settings.js](public/page-settings.js)의 별도 설정입니다.

소켓을 유지하면 작은 Ping/Pong 통신이 발생하고, 화면·탭 수와 데이터 변경 빈도가 늘수록 전송량이 증가합니다. 소켓 화면의 상단 상태 표시는 기존 소켓 이벤트만 관찰하므로 별도 확인 통신을 추가하지 않습니다.

### 채널별 데이터

| 채널 | 입력 상태 | 실제 출력 상태 | 장치 → 서버 문자열 | 서버 → 장치 문자열 |
| --- | --- | --- | --- | --- |
| 1~8 | `IS1`~`IS8` | `OS1`~`OS8` | `IStr1`~`IStr8` | `OStr1`~`OStr8` |

`InputSignal`, `OutputSignal`은 채널 식별자입니다. `OutputState`는 장치가 보고한 실제 출력 상태이며, `severSignal`은 요청 상태입니다. `severSignal`은 현재 규약의 철자를 그대로 사용합니다.

### 입력 변화와 웹 명령

1. 논리 IS 변화는 감지한 같은 호출에서 대응 OS로 반영하고 보고를 예약합니다. D7 물리 버튼은 50ms 유지 조건을 통과한 입력만 반영하며 통신 복구 시 최신 상태를 보고합니다.
2. 웹 버튼은 장치 ID·출력 채널·요청 상태·OStr를 서버에 보냅니다.
3. 서버는 권한을 확인해 명령을 DB에 저장하고 장치로 전송합니다.
4. 장치는 명령을 출력에 적용한 뒤 ACK와 실제 상태를 보고합니다.
5. 서버는 실제 상태를 저장하고 브라우저가 출력 표시·버튼 상태를 갱신하도록 전달합니다.

명령 저장·전달만으로 실제 출력 표시를 바꾸지 않습니다. 웹 명령은 IS를 바꾸지 않으므로 IS와 OS가 서로 다를 수 있고, 다음 안정된 입력 변화가 출력을 다시 갱신합니다. 마지막으로 처리된 입력 변화 또는 웹 명령이 출력에 적용됩니다.

### 메시지 종류

| 방향 | `type` | 역할 |
| --- | --- | --- |
| 장치 → 서버 | `hello` | 8채널 확인, 연결 등록, 대기 명령 처리 시작 |
| 장치 → 서버 | `state` | 입력·출력 상태, 문자열, 출처, IP 보고 |
| 장치 → 서버 | `channelString` | IStr만 갱신. 출력 문자열·상태는 유지 |
| 장치 → 서버 | `ack` | 장치·명령·채널·실제 상태 확인 후 성공/실패 기록 |
| 서버 → 장치 | `command` | 출력 요청 상태와 OStr 전달 |
| 브라우저 → 서버 | `subscribeDevice` | 초기 상태·이력·명령 구독 |
| 브라우저 → 서버 | `lamp` | 권한 검사를 거치는 출력 제어 요청 |
| 서버 → 브라우저 | `deviceSnapshot`, `state`, `stateChanged`, `channelString`, `deviceConnection` | 초기·실시간 상태와 연결 여부 전달 |
| 서버 → 브라우저 | `commandQueued`, `commandAck` | 명령 저장·처리 상태 알림 |

서버가 장치에 보내는 명령 예시는 다음과 같습니다.

```json
{
  "type": "command",
  "deviceId": "DEVICE-D1-001",
  "commandId": "UUID",
  "OutputSignal": "OS1",
  "InputSignal": "IS1",
  "severSignal": "ON",
  "OStr": "MOTOR_ON"
}
```

출력 문자열은 `OStr` 하나로 전송합니다. 명령에 OStr가 빈 문자열로 포함되면 장치는 저장된 OStr 표시값을 비우고, 값이 있으면 해당 값으로 갱신합니다. ACK에 문자열 정보가 없는 경우에는 서버가 기존 정보를 유지합니다.

### 동기화와 명령 상태

- 장치 메시지는 인증 완료를 기다린 뒤 수신 순서대로 처리합니다.
- 초기 API 조회 전에 받은 실시간 이벤트를 보관하여 오래된 조회 결과가 최신 상태를 덮어쓰지 않게 합니다.
- `PENDING`은 저장·대기, `DELIVERED`는 소켓 전송, `ACKED`는 성공 확인, `FAILED`는 실패, `CANCELLED`는 취소입니다.
- 오프라인 장치의 같은 채널에 쌓인 이전 대기 명령은 취소하고 최신 요청을 유지합니다. 재연결에서도 채널별 최신 대기 명령을 정리합니다.
- 출력이 같아도 입력·문자열·접속 시각은 갱신합니다. 출력 변경 이력과 마지막 변경자·변경 시각은 실제 출력이 바뀔 때 갱신합니다.

이전 주소·구독 이름·펌웨어 필드는 호환 처리에서만 인식합니다. 기존 `D8/D9/D10/D11` 명령은 `OS1/OS2/OS3/OS4`로 변환되며, 새 송신 메시지는 `InputSignal`·`OutputSignal`을 사용합니다.

### 데이터베이스 구조

| 테이블 | 저장 정보 |
| --- | --- |
| `user_profile` | 회원정보, 비밀번호 해시, 상태, 권한, 관리자 메모 |
| `product` | 제품, 생산수량, 목표수량, 상태, 변경 회원과 시각 |
| `user_setting` | 회원별 알림·테마·표시·날짜 설정 |
| `device` | 장치 ID·이름·토큰 해시·활성 여부·순서·IP·접속 시각 |
| `device_channel` | 8채널 이름, IS/OS 식별자, 독립 입력·출력 상태, 송수신 문자열 |
| `device_schedule` | 채널별 예약, 반복 조건, 실행 시각, 처리 상태와 예약자 |
| `device_command` | 명령 ID, 요청 출력, 문자열, 요청자, 처리 상태와 시각 |
| `device_state_history` | 출력 변경 전후 값, 출처, 당시 문자열, 변경 시각 |

기본 DB 이름은 `factory`이며 배포 환경의 실제 이름과 `DB_NAME`을 일치시킵니다. 테이블과 컬럼은 소문자 `snake_case`를 사용하며, 관리·조회·제어 페이지는 같은 도메인 테이블을 공유합니다. 회원관리와 회원정보를 별도의 테이블로 분리하지 않습니다.

| 테이블 | 변경된 컬럼 |
| --- | --- |
| `user_profile` | `id → user_id`, `name → user_name`, `status → user_status` |
| `product` | `id → product_id`, `status → product_status`, `active → is_active` |
| `device` | 숫자 PK `id → device_row_id`. 문자열 `device_id`는 유지 |
| `device_channel` | `id → channel_id` |
| `device_command` | 숫자 PK `id → command_row_id`. 명령 UUID `command_id`는 유지 |
| `device_state_history` | `id → history_id` |

나머지 명확한 컬럼명은 유지합니다. 서버는 SQL 별칭으로 API 응답의 기존 `id`·`name`·`status`를 보존합니다. HTTP API 주소, WebSocket 이벤트와 `InputSignal`·`OutputSignal`·IStr·OStr 통신 필드는 변경하지 않습니다.

현재 8채널 상태는 `device_channel`에서만 관리합니다. `device`에는 등록·인증·접속 정보만 보관하며 첫 4채널 중복 상태와 구형 D7 컬럼은 만들지 않습니다.

### 이력과 삭제 관계

`signal_message`에는 장치 입력으로 출력이 바뀌면 IStr, 웹 명령으로 바뀌면 OStr를 당시 값으로 저장합니다. 현재 문자열이 나중에 바뀌어도 과거 이력은 유지되며 문자열만의 갱신은 출력 변경 이력을 만들지 않습니다.

장치를 삭제하면 관련 채널·명령·이력도 외래키의 `ON DELETE CASCADE`로 삭제됩니다. 회원 삭제 시 개인 설정은 함께 삭제하고, 제품의 변경 회원 참조는 `NULL`로 바꿉니다. 제품 자체는 유지됩니다.

### 신규 DB 초기화와 재시작

초기 SQL과 서버의 `ensureSchema()`·`ensureDeviceSchema()`는 같은 8개 테이블 정의를 사용합니다. 신규 설치에는 컬럼·인덱스·외래키를 생성 시점에 정의합니다. 서버는 기존 설치를 위해 누락된 `device_command.istr_payload`를 추가하고, 예약 테이블에 `istr_payload`만 있으면 내용을 보존해 `ostr_payload`로 이름을 변경하는 호환 처리를 수행합니다. 테이블 이름 변경이나 일반 구형 DB의 자동 변환은 하지 않습니다. 새 장치에는 IS1~IS8·OS1~OS8의 8채널을 생성합니다.

현재 버전으로 생성된 DB는 재시작해도 유지됩니다. `CREATE TABLE IF NOT EXISTS`는 존재하는 테이블을 다시 만들지 않고, 기본 장치의 기존 이름·토큰 해시와 기존 채널 설정도 보존합니다. 이전 버전 DB의 자동 업그레이드는 지원하지 않습니다.

### 수동 이름 마이그레이션

[migrate-schema-names.sql](migrate-schema-names.sql)은 이름 변경 직전의 7개 테이블(`users`·`products`·`user_settings`·`devices`·`device_channels`·`device_commands`·`device_state_history`)에 한 번만 적용하는 파일입니다. DB 이름이나 데이터 값은 변경하지 않고 테이블·컬럼·일부 인덱스 이름과 외래키를 변경합니다. 예약 기능을 이미 사용하던 DB는 예약 테이블 변경에 [migrate-device-schedule.sql](migrate-device-schedule.sql)이 별도로 필요할 수 있습니다. 두 파일 모두 적용 전 백업하고, 현재 구조나 다른 구형 구조에 임의로 실행하지 않습니다.

1. 모든 서버 인스턴스와 DB 쓰기를 중지합니다.
2. 전체 DB를 백업하고 별도 환경에서 백업 복원을 확인합니다. 테이블별 행 수와 주요 회원·장치·생산 값도 기록합니다.
3. 대상 DB와 이전 컬럼·외래키 이름이 일치하는지 확인합니다. DDL 변경 권한을 가진 계정으로 마이그레이션을 실행합니다.
4. 새 테이블·컬럼·외래키와 행 수, 비밀번호 해시·장치 토큰 해시·채널 상태·설정·이력 값이 유지되는지 확인합니다.
5. 검증 후 변경된 서버를 시작하고 로그인, 설정, 제품, 장치 조회·제어를 확인합니다.

Git Bash에서 실행하는 예시입니다. 실제 DB 이름과 계정으로 바꾸며 `--force`를 사용하지 않습니다. MariaDB 환경에서는 대응하는 `mariadb-dump`·`mariadb` 명령을 사용할 수 있습니다.

```bash
mysqldump --single-transaction -u factory_user -p factory > factory-before-names.sql
mysql --default-character-set=utf8mb4 -u factory_user -p factory < migrate-schema-names.sql
```

DDL은 자동 커밋되어 SQL 트랜잭션으로 전체를 롤백할 수 없습니다. 중간에 실패하면 서버를 계속 중지한 채 백업으로 복구하고 원인을 확인합니다. 부분 적용 상태에서 파일을 다시 실행하지 않습니다. 마이그레이션을 적용하기 전에는 변경된 서버를 재시작하지 않습니다.

### 화면 설정과 스타일

브라우저 탭 제목은 [public/page-settings.js](public/page-settings.js)의 `PAGE_TITLE` 한 곳에서 관리하며 현재 값은 `KIMS SMART FACTORY`입니다. HTML의 `<title>`은 스크립트 적용 전의 초기 표시입니다. 화면 내부 제목은 별개입니다.

상단 사용자 표시는 `applyPageUser()`와 `refreshPageUser()`가 담당합니다. 화면 복귀 시 회원정보·권한을 다시 읽어 메뉴 표시를 갱신합니다.

상단은 브랜드 → 분류 문구 → 페이지 제목의 세 줄 구조입니다. 분류 문구는 [public/style.css](public/style.css)의 CSS 가상 요소로 관리합니다.

| 페이지 그룹 | 선택자 | 분류 문구 |
| --- | --- | --- |
| 생산 현황·제품 입력·제품 관리 | `.product-heading > .product-eyebrow::before` | `PRODUCT CONTROL` |
| 회원관리·회원정보·개인 설정·로그인·가입 | `.user-heading > .user-eyebrow::before` | `USER CONTROL` |
| 장치 조회·제어·관리 | `.device-heading > .device-eyebrow::before` | `DEVICE CONTROL` |

일반 페이지의 제목 시작 위치는 장치 제어 화면을 기준으로 맞춥니다. 공통 최대 폭은 `--page-max-width: 1240px`이며 화면 크기별 여백과 스크롤바 공간 고정으로 전환 시 흔들림을 줄입니다. 로그인·가입 페이지는 예외적으로 아래 폼 폭에 맞춰 헤더를 정렬하고 `--auth-content-width`를 각각 470px·940px로 사용합니다.

CSS는 번호가 붙은 11개 구역으로 나누어져 있습니다. 공통 색상·글꼴은 `--factory-*`, 페이지별 호환 변수는 `--site-*`와 `--device-*`입니다. 해당 기능의 기존 구역과 선택자를 우선 수정하고 중복 선언을 불필요하게 추가하지 않습니다.

```bash
npm test
npx prettier public/style.css --check --tab-width 2 --print-width 100
```

`npm test`는 DB·브라우저·소켓을 모의하여 회귀 동작을 확인합니다. 실제 DB 접속·마이그레이션, PlatformIO 빌드, 장치 통신은 별도로 검증해야 합니다. 현재 `check:css` 스크립트는 삭제된 `test/css-structure.test.js`를 참조하므로 CSS 형식만 검사할 때는 위의 Prettier 명령을 사용합니다.

CSS를 의도적으로 수정한 뒤 형식을 정리할 때만 다음 명령을 사용합니다.

```bash
npm run format:css
```

테스트는 모의 DB·소켓·DOM으로 신규 테이블 생성·초기 SQL 일치·재시작·관리자 생성, 권한, 개인 설정, 8채널 등록, 메시지 순서, ACK, 문자열 보존, 실제 상태 반영, CSS 구조를 확인합니다. 실제 DB 생성·연결과 보드 통신은 별도 확인이 필요합니다.

코드 설명은 각 파일의 역할과 판단 이유를 주석으로 기록합니다. 요청 상태와 실제 상태, 개인 설정과 공용 데이터, 최신 이벤트와 초기 조회를 구분하고, 주석만 정리할 때 함수·변수·이벤트·DB 구조는 변경하지 않습니다. 권한·DB·장치 안내는 실제 코드와 테스트를 기준으로 함께 갱신합니다.
